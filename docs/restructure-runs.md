# 재구성 3회 비교 (Run 1 · 2 · 3)

같은 브리프("고령자가 이체 과업을 끝낼 수 있게 화면을 다시 설계하라")로 만든 세 재구성본을
같은 검사기(`senior_ui/audit/`)로 검사한 결과. 질문은 하나다 — **설계 편차가 결과 차이로
이어지는가.**

| | 파일 | 흐름 파일 | 화면 수 |
|---|---|---|---|
| Run 1 | `outputs/restructured_transfer.html` | `flows/restructured.json` | 9 |
| Run 2 | `outputs/restructured_run2.html` | `flows/run2.json` | 7 |
| Run 3 | `outputs/restructured_run3.html` | `flows/run3.json` | 8 |

세 파일 모두 `results/` 에 사본이 있고, 검사 스크린샷은 `results/shots/{restructured,run2,run3}/`.

## 세 설계가 어디서 갈라지나

세 Run 은 시작·받는 사람·금액·확인·완료 화면과 CSS 토대를 공유한다. 갈라지는 지점은
"어디서 화면을 자르는가" 뿐이다.

| 단계 | Run 1 (9) | Run 2 (7) | Run 3 (8) |
|---|---|---|---|
| 계좌번호 입력 | `accno` 화면 | `account` 화면 | `accno` 화면 |
| 은행 확인 | `bank` 화면 — "이 은행이 맞나요?" 예/아니오 | **계좌 화면 안의 띠.** 10자리 넘으면 "카카오뱅크 번호입니다 [아니에요]". 추정 실패 시에만 목록 패널이 덮음 | Run 1과 같음 |
| 예금주 확인 | `whoconfirm` 화면 — 이름만 크게, 예/아니오 | **금액 화면 상단 카드.** 이름·은행·계좌 표시 + [다른 분이에요]. [다음]이 곧 확인 | Run 1과 같음 |
| 본인 확인 | `auth` 화면 — 지문/비밀번호 선택 | Run 1과 같음 | **확인 화면 위 모달.** [보내기] 누른 자리에서 뜨고 [취소]하면 그대로 확인 화면 |

## 검사기 결과 — 셋이 구분되지 않는다

| 지표 | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| passed / fatal / warning — 옛 검사기 | ✓ / 0 / 0 | ✓ / 0 / 0 | ✓ / 0 / 0 |
| passed / fatal / warning — 현재 (v3) | ✗ / 3 / 3 | ✗ / 3 / 3 | ✗ / 3 / 3 |
| 화면 도달 | 9/9 | 7/7 | 8/8 |
| 완료 화면 금액 | 10,000 | 10,000 | 10,000 |
| data-action 수 / 처리된 수 | 31 / 31 | 27 / 27 | 31 / 31 |
| 죽은 컨트롤 | 0 | 0 | 0 |
| 저대비 텍스트 (원본 66) | 3 | 3 | 3 |
| 겹침 / 넘침 / 미정의 클래스 | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |
| 새 영어 단어 | 0 | 0 | 0 |

검사기가 보는 한 세 설계는 **동일하다.** 화면 수가 7·8·9로 다르고 확인 지점이 다른데도
어떤 지표도 갈라지지 않는다. 이것이 이 비교의 결과다: 편차는 있지만 검사기가 그 편차를
측정하지 못한다.

**첫 행 말고는 v3 에서도 수치가 같다** — 화면 도달, 완료 화면 금액, data-action
수/처리된 수, 죽은 컨트롤, 저대비 텍스트 3건, 겹침/넘침/미정의 클래스, 새 영어
단어가 모두 그대로다. 바뀐 것은 판정이다. 옛 검사기: 셋 다 통과 (fatal 0 /
warning 0) / 현재: 셋 다 통과 못 함 (fatal 3 · warning 3). fatal 3 은 검사 I
(선택지 보존), warning 3 은 검사 D (기준 미달 대비)다. 측정값은
`results/audit_*.v3.json`.

"저대비 텍스트 (원본 66)" 의 **원본 66 은 지금 검사기가 더 내놓지 않는 수치다.**
검사 D 의 전후 비교가 새 설계에서는 내려가고(`checks_stood_down`) v3 의
`low_contrast_before` 는 `null` 이다 — 이름만 같은 남의 화면과 견주던 것을
막은 결과다. 생성물 쪽 3건은 옛 검사기와 같고, 그 3건이 v3 에서는 warning 3건이
된다 (눌릴 수 없는 '다음' 버튼 2.52:1 둘, 금액 자리 '0원' 2.61:1).

## 검사기가 못 보는 것 — 손으로 센 것

| | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| 처음 보내는 계좌, 탭 수 (13자리 + 금액 5자리 + 비밀번호 4자리 포함) | 30 | **28** | 30 |
| 저장된 사람, 탭 수 | 14 | 14 | 14 |
| 돈이 나가기 전 **명시적 예/아니오** 횟수 | 3 (은행·예금주·최종) | **1** (최종만) | 3 |
| 최종 확인에서 본인 확인까지 화면 전환 | 1 | 1 | **0** (모달) |
| 화면당 결정 수가 2 이상인 화면 | 0 | **1** (`account`: 번호 + 은행) | 0 |

Run 2 가 2탭 짧은 대신 확인 두 개를 잃었다. 원본 `account` 화면의 문제(번호 입력과 은행
선택이 한 화면, changelog #11)를 Run 1 이 분할로 풀었는데 Run 2 는 다시 합쳤다 — 띠로
보여줘서 원본보다는 낫지만 "한 화면에 두 결정"이라는 구조는 돌아왔다. Run 3 은 Run 1 과
탭 수가 같고, 모달이라 "보내기 → 본인 확인 → 완료" 사이에 화면이 통째로 바뀌는 일이 한 번
준다. 대신 모달 뒤로 확인 내용이 비쳐 보이는 것이 고령자에게 도움인지 방해인지는 모른다.

어느 쪽이 나은지는 이 문서가 답하지 않는다. 답하는 것은 **차이가 어디에 있고, 지금 검사기가
그 차이에 눈을 감고 있다는 것**이다. 검사기에 "돈이 나가기 전 명시적 확인 횟수"와 "화면당
결정 수"를 넣으면 셋이 갈라진다. 그 두 지표가 곧 KB 에 없는 구조 규칙의 후보다
(`restructure-changelog.md` 3절).

## 이 비교의 한계

1. **Run 2·3 은 Run 1 에 닻내림돼 있다.** 같은 대화에서 연달아 설계했고, 이 구현은 그 설계
   표의 요약("은행→계좌 화면, 예금주→금액 화면 / 본인 확인→모달")만 보고 Run 1 의 코드를
   바탕으로 만들었다. 공유 CSS·문구·동작이 같은 것은 우연이 아니라 그 때문이다. 따라서
   여기서 잰 편차는 **하한**이다. 서로 모르는 세 세션에서 같은 프롬프트로 돌려야 진짜
   편차가 나온다 (`CONTINUE.md` 남은 일 3).
2. 은행 추정(`3333` → 카카오뱅크)은 세 Run 모두 시제품 안의 표로 흉내 냈다. 실제 SOL 에
   그 기능이 있는지는 확인 안 됨.
3. 예금주 조회는 세 Run 모두 `김시현` 고정이다. 어느 계좌를 쳐도 같은 이름이 나온다.

## 재현

```powershell
cd C:\Users\xihye\senior-ui-pipeline
.\.venv\Scripts\python.exe -m http.server 3003 --directory .   # 다른 터미널
foreach ($r in "run2","run3") {
  .\.venv\Scripts\python.exe -m senior_ui.audit --flow flows\$r.json `
     --build http://localhost:3003/outputs/restructured_$r.html `
     --build-file outputs\restructured_$r.html `
     --out outputs\audit_$r.json --shots outputs\shots\$r
}
.\.venv\Scripts\python.exe -m senior_ui.collect_results
```

위 표의 `fatal 0 / warning 0` 은 검사 I(선택지 보존, `b2db795`)가 생기기 전의
값이다. 지금 검사기로 같은 명령을 돌리면 셋 다 I 에서 fatal 1건이 난다 (원본
`pick-bank` 67개 중 58개 누락). 측정값은 `tests/baseline/` 에 있다.

**이 단락의 `fatal 1` 도 이제 옛 수치다** — 검사기 3·4-1·4-2단계
(`fix/audit-counting` · `fix/audit-accuracy-1` · `fix/audit-accuracy-2`) 이전
기준이다. 옛 검사기: fatal 1 / 현재: fatal 3 · warning 3. 검사 I 가 낱말 단위로
찾게 되면서 `pick-bank` 67개 중 58개 누락에 `quick` 4개 중 1개(`all`)와 `num`
11개 중 1개(`00`)가 더해져 3건이 되고, 검사 D 가 기준 미달 대비를 하나씩
경고하면서 warning 3건이 난다. 측정값은 `results/audit_*.v3.json` 이고
`tests/baseline/` 의 기준값도 같이 다시 뽑혔다.
