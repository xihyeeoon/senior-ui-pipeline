# 공과금 원본 HTML — 범위와 크기 (1단계)

`inputs/original_bill.html` 을 만들기 전에 범위를 정하려는 문서다. 기준은 Flutter
더미앱(`senior-ui-dummy-app`, 커밋 `00834ca`)의 A1 공과금 경로다. 캡처는 대조용으로만
본다.

눌러도 아무 일이 없다(기록만 남는다). HTML 에서도 아무 일도 하지 않는다. 범위 밖이
아닌데도 더미앱에서 반응이 없는 장식은 "장식" 으로 따로 적었다.

## 3. 전체메뉴와 검색을 어디까지 넣나

### 더미앱의 메뉴 크기

대분류 7 · 소분류 61 · 항목 293 (`lib/data/sh_menu_data.dart`). 은행 탭만 소분류 10 ·
항목 69 이다. 과제와 헷갈릴 만한 항목이 다른 탭에 있다 — **카드 › 대표 생활요금 ›
전기 요금** (·도시가스 요금·전화 요금), 카드 › 이용금액 결제 › 분할납부. 더미앱에서
"전기" 를 검색하면 결과는 카드의 **전기 요금** 하나뿐이고, 누르면 아무 일도 없다.

### 선택지

| | A. 전부 | B. 은행 탭 + 헷갈리는 항목 (추천) | C. 과제 섹션만 |
|---|---|---|---|
| 메뉴 | 7탭 · 61섹션 · 293항목 | 은행 탭 전부(10섹션 · 69항목) + 카드 › 대표 생활요금 섹션. 나머지 탭은 탭 바 이름만 (눌러도 무동작) | 은행 탭의 칩 10개 이름 + 세금/공과금 섹션 6항목. 나머지는 탭 이름만 |
| 검색 | 293항목 + 별칭 "공과금납부" | 넣은 항목 + 별칭 | 넣은 항목 + 별칭 |
| 더미앱과 다른 점 | 없음 | "납부" 검색에서 카드 › 분할납부가 빠진다. 다른 탭 내용이 없다 | 메뉴를 훑어 찾는 수고가 거의 사라진다. "전기" 검색 결과가 0건이 된다 |
| 예상 크기 (토큰) | 약 12,100 (11,500~13,000) | 약 10,100 (9,500~10,800) | 약 9,600 (9,000~10,300) |

| 이체 원본(11,086) 대비 | **+약 1,000** | −약 1,000 | −약 1,500 |
| 생성 프롬프트 (이체 15,200 기준) | 약 16,200 | 약 14,200 | 약 13,700 |

(C 에서 검색까지 빼면 약 8,900 이지만, 검색 화면이 없어져 과제의 둘째 길이 사라진다.)

### 어림 방법

토큰은 저장소의 `restructure/model.estimate_tokens` (tiktoken `o200k_base`) 로 셌다.
이체 원본은 11,086 토큰, 36,327 글자다 (글자/토큰 3.28).

- **잰 것**: 메뉴 데이터를 스크립트 배열(탭별 칩 · 섹션 크기 · 항목 라벨)로 적은 크기 —
  A 2,511 · B 536(+대표 생활요금 약 60) · C 64(+칩 이름 약 40). 이체 원본의 홈 화면
  1,305, 스타일 4,408, 스크립트 3,054.
- **어림한 것** (공통부 약 8,200): 스타일 약 3,200 (이체보다 부품이 적다), 스크립트 공통
  (기록 장치·화면 전환·처리기·비밀번호 키패드·납부 항목 그리기) 약 1,900, 홈 1,310
  (이체 원본 그대로 + 메뉴 진입), bill-home 약 700 (항목 18개 배열 포함), camera 150,
  info 400, password 140, done 420. 메뉴 화면 틀과 그리는 스크립트 약 600, 검색 화면과
  스크립트 약 650.
- 가장 불확실한 것은 스타일이다. 실제로 만든 뒤 잰 값을 2단계 보고에 적는다.

### 추천: B

- 이체 원본보다 작다 — 재시도가 지금보다 빠듯해지지 않는다.
- 고령 사용자가 실제로 겪는 부분이 남는다: 긴 은행 탭을 훑어 **세금/공과금 › 납부하기**
  를 찾는 일, 카드 탭의 **전기 요금** 이라는 헷갈리는 항목, 그리고 "공과" 와 "전기"
  검색 결과가 더미앱과 같다.
- A 와 B 의 차이는 약 2,000 토큰이고, 그 대부분은 카드·증권·보험·혜택 항목 220개다.
  재설계 결과(디자이너용 구조 시안)에서 그 항목들의 배치는 과제와 관계가 적다.

## 4. 오류 팝업

**더미앱 공과금 경로에는 오류 팝업이 없다.**

| 화면 | 확인한 것 | 결과 |
|---|---|---|
| menu · search | 메뉴 항목 · 검색 결과를 누를 때 | 과제 항목은 이동, 나머지는 범위 밖(실험 빌드에서 무반응). 팝업 없음 |
| search | 1글자 입력 | "검색버튼(돋보기)을 눌러주세요" 안내 — 팝업이 아니라 같은 화면의 다른 상태다. [확인] 도 없다 |
| camera | 셔터 | 판정 없이 납부정보로 |
| info | [납부] | 판정 없이 비밀번호로. 금액·계좌가 고정값이라 틀릴 입력이 없다 |
| password | 4자리 | **판정 없음** — 어떤 4자리도 통과 (`a1_bill_pay_password.dart`: "실제 검증은 없다(더미)") |

더미앱의 오류 팝업 둘(`ELB00016`, `ETA00325`)은 이체 전용이다
(`ScreenNames.errorDialog`, `ShDummy.checkTransfer`).

그래서 흐름 파일의 `error_paths` 는 빈 목록이 되고, `truth` 의 틀린 값(`*_WRONG`)은
쓸 곳이 없다. 9-2번 형식의 오류 경로를 만들려면 더미앱에 없는 오류를 지어내야 한다 —
그것은 "더미앱과 같아야 한다" 에 어긋나므로 만들지 않는 쪽을 추천한다.

## 5. 정한 것 (2026-10-05)

1. **범위는 지금 B 다. A 로 바꿀 자리를 둔다.** 최종 범위는 계정의 분당 한도를 확인한
   뒤 정한다. 바꾸는 법은 6절.
2. **B 는 홈 · 은행 탭 · 공과금 경로만 재설계 대상이다.** 나머지 탭은 이름만 넣었고

   그대로 둔다.
3. 정답 경로는 검색을 거친다. 메뉴에서 바로 가는 길은 `tests/test_original_bill.py`

4. 사용자가 고르는 목록은 과제 밖이어도 `data-action` 을 붙여 데이터 보존 대상으로
   한다. 누르면 아무 일도 하지 않는다 (`docs/input-contract.md` 의 규칙).
5. 오류 경로는 없다 (`error_paths: []`, 틀린 값 없음).

## 6. A 판을 만드는 법

메뉴 데이터는 `inputs/original_bill.html` 스크립트의 **탭별 배열 일곱 개**다. B 판은
`MENU_BANK` 만 다 채웠고, `MENU_CARD` 는 대표 생활요금 섹션만, 나머지 다섯은 빈 배열
(`[]`)이다.

| 탭 | 배열 | B 판 | A 판 (`docs/bill-menu-full.json`) |
|---|---|---|---|
| 은행 | `MENU_BANK` | 10섹션 · 69항목 (A 와 같다) | 10 · 69 |
| 카드 | `MENU_CARD` | 대표 생활요금 1섹션 · 4항목 | 16 · 61 |
| 증권 | `MENU_STOCK` | `[]` | 12 · 60 |
| 보험 | `MENU_INSURE` | `[]` | 12 · 43 |
| 혜택 | `MENU_BENEFIT` | `[]` | 6 · 35 |
| 상품 | `MENU_GOODS` | `[]` | 4 · 14 |
| 고객센터 | `MENU_HELP` | `[]` | 1 · 11 |

배열 원소의 모양: 소분류마다 `'#소분류 이름'` 한 칸, 그 뒤에 그 소분류의 항목들.
`bill-menu-full.json` 의 `tabs[i].sections[j]` 를 순서대로 `'#' + chip`, `items…` 로
펼치면 된다. 그 밖에는 아무것도 고치지 않는다 — 탭 바 · 칩 · 검색 · 보존 대상이 모두
이 배열에서 나온다. 같은 흐름 파일(`flows/original_bill.json`)이 그대로 돈다.

```python
# A 판 만들기 (B 판의 배열 일곱 줄을 바꾼다)
import io, json, re
NAMES = {'은행': 'MENU_BANK', '카드': 'MENU_CARD', '증권': 'MENU_STOCK', '보험': 'MENU_INSURE',
         '혜택': 'MENU_BENEFIT', '상품': 'MENU_GOODS', '고객센터': 'MENU_HELP'}
s = io.open('inputs/original_bill.html', encoding='utf-8').read()
for tab in json.load(open('docs/bill-menu-full.json', encoding='utf-8'))['tabs']:
    vals = [v for sec in tab['sections'] for v in ['#' + sec['chip']] + sec['items']]
    new = "const %s = [%s];" % (NAMES[tab['tab']], ",".join("'%s'" % v for v in vals))
    s = re.sub(r"const %s = \[[^\]]*\];" % NAMES[tab['tab']], lambda m: new, s)
```

2단계에서 이 방법으로 A 판을 만들어 흐름 파일로 끝까지 걸었다 (8화면 모두 도달,
`preserved_data()` 가 배열 열 개를 뽑는다).

## 7. 만든 뒤 잰 크기

`restructure/model.estimate_tokens` (tiktoken `o200k_base`). 생성 프롬프트는 지금의
`docs/restructure-prompt.md` 템플릿에 원본 · 선택지 요약 · 오류 조건을 넣고 잰 값에,
계획(plan) 글 약 1,200 을 더했다 (이체에서 사용자가 준 15,200 과 템플릿만으로 잰
14,002 의 차이). 재시도는 생성 프롬프트에 앞 시도의 HTML(원본의 약 0.8배 — mock 재시도
프롬프트에서 잰 비율)과 흐름 · 검사 결과 약 1,000 을 더한 어림이다.

| | 원본 토큰 | 원본 글자 | 선택지 요약 | 오류 조건 | 생성 프롬프트 | 재시도 프롬프트 (어림) |
|---|---|---|---|---|---|---|
| 이체 | 11,086 | 32,896 | 368 | 429 | 약 15,200 | 약 25,100 |
| **공과금 B** | **10,526** | 29,374 | 358 | 0 | **약 14,200** | **약 23,600** |
| 공과금 A | 12,201 | 32,066 | 455 | 0 | 약 16,000 | 약 26,800 |

1단계 어림(B 약 10,100 · A 약 12,100)과 잰 값의 차이는 400 · 100 이다. B 는 이체보다
560 작고, A 는 1,115 크다.

분당 한도가 3만이면: 한도는 입력에 `max_tokens` (생성 기본 14,000)를 더해 세므로, 재시도
요청은 "Request too large" 로 한 번 돌아오고 루프가 `max_tokens` 를
`30,000 − 입력 − 500` 으로 줄여 다시 보낸다 (`model.shrink_for_minute`). 줄인 값이
`MIN_COMPLETION` 4,000 보다 작으면 기다리지 않고 멈춘다 (`RateLimited`).

| | 재시도 입력 (어림) | 줄인 `max_tokens` | |
|---|---|---|---|
| 이체 | 약 25,100 | 약 4,400 | 겨우 넘는다 (지금 "빠듯하다" 의 정체) |
| 공과금 B | 약 23,600 | 약 5,900 | 넘는다 |
| 공과금 A | 약 26,800 | 약 2,700 | **4,000 미만 — 재시도가 멈춘다** |

어림이므로 몇백 토큰은 흔들리지만, A 는 3만 한도에서 재시도가 돌지 않을 가능성이 높다.
A 로 가려면 분당 한도가 약 3.2만 이상이어야 한다 (입력 26,800 + 최소 답 4,000 + 500).

## (1단계 보고 때의 질문 — 위 5절로 정했다)

1. **범위**: A / B / C. 추천 B.
2. **정답 경로(`steps`)는 검색을 거쳐 간다** (home → menu → search → bill-home → …).
   화면 덮기 규칙("모든 화면은 정답 경로나 오류 경로 중 하나가 지나간다") 때문이다. 오류
   경로가 없으니 메뉴 목록에서 바로 **납부하기** 를 누르는 길로 가면 search 화면을
   아무도 지나가지 않는다. 검색을 거치는 길이 더 길기도 하다 (재구성 프롬프트는
   `steps` 를 "가장 긴 경로" 로 쓴다). 메뉴 목록에서 바로 가는 길은
   `tests/test_original_bill.py` 에서 따로 걷는다. — 다른 방법이 좋으시면 알려 주십시오.
3. **범위 밖 목록에 `data-action` 을 붙일지.** 말씀하신 대로 납부 항목 18개 · 메뉴
   항목은 스크립트 배열로 그린다. 그런데 데이터 보존 장치는 `data-action` 이 붙은
   묶음만 보호하고, 입력 계약은 "과제 경로 밖 요소에는 `data-action` 을 붙이지 않는다"
   이다.
   - 메뉴 항목은 **납부하기** 가 같은 묶음 안에 있으니 묶음 전체에 `data-action` 을
     붙인다 (이체 원본의 은행 목록과 같다 — 신한 하나만 정답이어도 38개 모두 붙어 있다).
   - **납부 항목 18개는 모두 과제 밖이다.** 추천: `data-action="pick-bill"` 을 붙이고
     처리기는 아무것도 하지 않는다 (보호된다. 탭 기록에 `valid:true` 로 남는다 — 더미앱도
     범위 밖 탭을 따로 기록한다). 다른 길: 붙이지 않는다 (계약대로. 보호되지 않아 재설계에서
     항목이 줄 수 있다).
   - 출금계좌는 하나뿐이고 더미앱에서 고를 수 없다. 원소 하나짜리 묶음은 선택지로 세지
     않으므로 배열로 두어도 보존되지 않는다. 그냥 글자로 둔다.
4. **오류 경로 없음** 으로 둔다 (`error_paths: []`, `*_WRONG` 없음). 검사기가 빈 목록을
   어떻게 다루는지는 3단계 원본 대 원본 검사에서 확인해 보고한다.

## 8. 원본 대 원본 검사와 이체 전용 부분 (11번 단계의 재료)

검사기 · 재구성 루프 코드는 고치지 않았다. 아래는 확인만 한 것이다.

**원본 대 원본 (공과금).** `python -m senior_ui.audit --original/--build …/original_bill.html
--flow flows/original_bill.json` → **통과**. fatal 0, warning 2 (홈 마이신한포인트 띠의
그라디언트 위 글자 — 이체 원본과 같은 두 건), 8화면 모두 도달, 완료 금액 2,160. 검사 J 는
오류 경로가 없어 물러난다. 통과한 것은 공과금 흐름이 이체 전용 요구를 **맞춰 줬기**
때문이다 — 아래 1·2.

**이체 전용이라 공과금에서 떨어지거나 맞춰 줘야 하는 것:**
