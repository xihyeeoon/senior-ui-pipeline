# 편차 기록

같은 프롬프트로 재구성을 돌릴 때마다 무엇이 달라지는지 모아 둔다. 편차의 종류를
쌓는 것이 목적이고, 어느 설계가 낫다는 판단은 여기서 하지 않는다.

손으로 만든 Run 1·2·3 의 비교는 `restructure-runs.md` 에 있다. 이 문서는 그 뒤에
`python -m senior_ui.restructure` 로 자동 생성한 것들을 기록한다.

- `who` 화면에 은행 선택 + 계좌번호 입력 동시 배치
- Run 1 은 같은 지점을 두 화면으로 분할했음
- 편차 유형: 화면 수(9·7·8)에 이어 **"분할 경계"** 에서도 불일치 확인

보존)다. 멈춘 지점(`amount`)과 도달 화면(6 중 2)은 그대로다.

## Run 4 (2026-10-01) — 자동 파이프라인 첫 통과

**검사 fatal 0 을 자동으로 달성한 첫 사례.** 시도 3 에서 통과했다 (형식 1회,
검사 1회 소모).
(검사 I 추가 이전 기준. 현재 기준은 아래 "지금 검사기로 다시 검사하면" 단락 참고)
(옛 검사기: fatal 0 / warning 8, 통과 / 현재(v3): fatal 2 / warning 8, 통과 못 함)

- 화면 7개: `start` · `account` · `bank` · `amount` · `confirm` · `password` · `done`
- 계좌와 은행을 **분리**했다 (자동 Run 3 과 같고 Run 2 와 다르다)
- 입력은 숫자판 20키 + `<input>` 4개 혼용
- 과제 완주: 8/8 도달, 완료 화면 금액 10,000 일치
- 저대비 66 → 0 (단 wireframe 단계라 D 는 검사하지 않았다)
- 남은 warning 8건은 전부 F(영어) — 상태바의 "LTE"

위 세 줄은 v3 에서도 그대로다 — 8/8 도달, 완료 금액 10,000 일치, warning 8건 전부
F(영어) `LTE`. 다만 **"저대비 66 → 0" 의 66 은 지금 검사기가 더 내놓지 않는
수치다** (검사 D 의 전후 비교가 새 설계에서 내려가 `low_contrast_before` 가
`null`). 생성물 쪽 0 은 그대로고, wireframe 단계라 D 는 여전히 검사하지 않는다.

실행: `outputs/restructure_auto/20261001-125247/`
(같은 폴더의 사본이 `results/runs/20261001-125247/` 에 있다 — 시도 1~3 의
프롬프트·응답·html·흐름·검사 결과, `run.log`, 스크린샷 전부)

통과를 만든 것은 검사기 메시지였다. 시도 2 는 일곱 화면 전부에서
`window.__screen()` 이 null 이었는데, 그 전까지 "landed on None instead" 라고만
알려 주던 것을 "기록 훅 `__screen()` 은 현재 화면의 id 를 반환해야 한다. 원본의
`__screen()` · `__startTask()` · `__dump()` 를 유지하라" 로 바꾸자 다음 시도에서
정확히 고쳤다. 모델의 문제라기보다 검사기가 무엇을 원하는지 말하지 않은 문제였다.

Run 4 는 검사 I(선택지 보존, `b2db795`) 가 생기기 전의 검사기로 통과했다. 지금
검사기로 다시 검사하면 I 에서 fatal 2건(`pick-bank` 67개 중 64개 누락, `quick`
4개 전부 누락)으로 통과하지 못한다. 그때 판정은 `results/audit_run4.json`, 다시
검사한 결과는 `results/audit_run4.recheck.json`.

**이 단락의 fatal 2 는 v3 에서도 같다** (`pick-bank` 64개 · `quick` 4개 누락).
함께 적을 수치는 warning 이다 — 옛 검사기: warning 8 / 현재(v3): warning 8, 둘 다
전부 F(영어) `LTE`. 다시 검사한 기록의 **지금 판본은 `results/audit_run4.v3.json`
이다** — `audit_run4.recheck.json` 은 집계 버그를 고치기 전(3단계 이전)의
기록이므로 더 이상 지금 수치가 아니다.

## 표 1. 같은 방식 내 편차 — 손수 제작 3회

같은 프롬프트로 같은 방식(대화로 직접 지시)을 세 번 돌려 나온 차이다. 조건이
같으므로 편차의 근거로 쓸 수 있다. 출처는 `restructure-runs.md`.

| 유형 | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| 화면 수 | 9 | 7 | 8 |
| 분할 경계 | 계좌·은행 **분리**, 예금주 확인 별도 화면 | 계좌 화면에 은행 **흡수**, 예금주 확인은 금액 화면에 | Run 1 과 같음 (본인 확인만 모달로) |
| 확인 지점 | 3 | 1 | 3 |

## 표 2. 방식 간 차이 — 손수 제작 vs 자동 파이프라인

**이 표는 편차의 근거가 아니다.** 각 방식의 표본이 부족해(손수 제작 3회, 자동 2회)
차이가 방식 때문인지 실행 간 흔들림인지 가릴 수 없다. 관측 기록일 뿐이다.

| 유형 | 손수 제작 (Run 1·2·3) | 자동 파이프라인 (Run 2·3) |
|---|---|---|
| 입력 방식 | 전부 숫자판 | Run 2 는 `<input>`, Run 3 은 숫자판, Run 4 는 혼용 |
| 화면 수 | 9 · 7 · 8 | 6 · 8 · 7 |

입력 방식은 자동 쪽 안에서도 갈린다. 자동 Run 2 만 `<input>` 을 썼고 Run 3 은
손수 제작과 마찬가지로 숫자판이다. 방식의 차이라고 부를 근거가 더 약해진다.

숫자판과 입력창은 고령자에게 과제 완수율이 갈릴 수 있는 차이다. 실험 자극물을
고를 때 이 항목이 고정되지 않으면, 결과를 도구의 효과로 귀속시킬 수 없다.

## 그 밖에 관측된 것

자동 실행에서만 나온 것들이다. 편차라기보다 결함에 가까워 `defect-types.md` 와
겹친다.

- **흐름 명세 자체의 오류** — 같은 화면 반복 지정(자동 Run 3), 숫자판과 입력 칸
  셀렉터 혼용(자동 Run 2)
- **분할 경계가 자동 실행 안에서도 갈림** — 자동 Run 2 는 계좌+은행을 합쳤고
  Run 3 은 분리했다. 표 1 의 손수 제작에서 본 것과 같은 종류의 흔들림이지만,
  자동은 아직 2회뿐이라 표로 만들지 않는다.
