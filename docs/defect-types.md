# 결함 유형

생성된 설계에서 반복해 나타나는 결함을 종류별로 모은다. 검사기가 자동으로 잡는
것과 아직 손으로만 발견한 것을 나눠 적는다. 아래쪽 목록이 검사기에 넣을 후보다.

## 검사기가 잡는 것

`senior_ui/audit/` 의 검사 A~K. 자세한 내용은 `README.md` 의 검사기 절에 있다.

| | 결함 | 심각도 |
|---|---|---|
| A | 과제를 끝까지 못 감, 구조 보존 실패, **기록과 화면 불일치** | fatal |
| B | 표시값이 입력과 다름, 주입된 대화상자 | fatal |
| C | **죽은 컨트롤** — `data-action` 은 있는데 처리기에 분기가 없다 | fatal |
| D | 대비 | warning |
| E | 레이아웃 (겹침·넘침·줄바꿈) | warning |
| F | 원본에 없던 영어 | warning |
| G | 상태가 시각적으로 구분되지 않음 | warning |
| H | 어느 스타일시트도 정의하지 않은 클래스 | warning |
| I | **선택지 누락** — 원본에서 고를 수 있던 값이 생성물에 없다 | fatal |
| K | **과제 밖 입구 삭제** — 과제에 쓰지 않는 메뉴 · 버튼(과제 파일의 `entrances`, 원본의 `data-action="oos-…"`)을 지우거나 늘 숨겨 과제를 쉬워 보이게 한다. 예비 실행 20261006-215902 와 실제 첫 답 sol 이 이체 홈의 다른 메뉴를 거의 다 지웠다 | fatal |
| J | **오류 경로** — 과제가 정한 잘못된 입력에서 오류 상태가 나타나지 않거나, 무엇이 틀렸는지 알리는 새 글이 없거나, 고칠 화면으로 되돌아가지 못한다 (알림 글에 과제 단어가 없으면 warning) | fatal |

### 완주 판정에서 새로 잡게 된 것 (A, 2026-10-04~05 추가)

검사기 4단계 수정(`fix/audit-accuracy-1`·`fix/audit-accuracy-2`)으로 잡게 된
것들이다. 셋 다 그 전에는 **통과로 읽혔다** — 결함이 없어서가 아니라 검사기가
보지 않아서다.

**기록만 넘어가고 화면은 안 넘어감** (fatal, 4-1단계 `d886385`). `window.__screen()`
은 다음 화면의 이름을 돌려주는데, 실제로 켜진 화면(`.screen.on`)의 `data-screen`
은 아직 앞 화면이다. 예외도 나지 않고 기록도 맞는 이름이라 기록 하나만 보면 완주한
것으로 보이는데, 사용자는 앞 화면에 그대로 서 있다. 이제 도착은 **기록과 켜진
화면이 둘 다 그 이름일 때만** 인정한다. 엉뚱한 화면에 도착한 것과 같은 멈춤으로
보므로 뒤 화면들은 파생으로 묶인다.

**켜진 화면이 없음** (fatal, 4-1단계 `d886385`). `.screen.on` 인 요소가 문서에
하나도 없다. 화면에 매인 probe 가 전부 null 로 돌아오고, 그 상태로는 무엇이 보이는지
하나도 잴 수 없다. 빈 목록을 통과로 읽으면 **아무것도 떠 있지 않은 빌드가 가장
깨끗해 보인다** — 저대비 0건, 겹침 0건, 미정의 클래스 0건이 된다.

**같은 화면 두 번째 방문이 첫 번째를 덮어씀** (4-2단계 `4c88bf1`). 흐름이 같은
화면을 두 번 지나가면 두 번째 방문의 측정이 첫 번째를 덮어썼다. 앞 방문에만 있던
결함은 사라지고, 뒤 방문에만 있던 결함은 앞 방문의 것으로 기록됐다. 이제 방문을
`account#2` 처럼 순서대로 남긴다. 그 자체로 fatal 을 내는 항목은 아니지만, 이것이
틀리면 화면별 판정 전체가 틀린다. 자동 Run 4 의 `account` 가 그 경우다
(`results/audit_run4.v3.json` 의 `screens_landed_on` 에 `account` 와 `account#2`
가 따로 있다).

### 선택지 누락 (I, 2026-10-01 추가)

과제가 쓰는 값 하나만 남기고 나머지를 지우는 최소 구현을 잡는다. 검사 과제는
카카오뱅크로만 송금하므로, 은행 목록에 카카오뱅크 하나만 있어도 A~H 는 전부
통과한다. 그러나 다른 은행을 쓰려던 사람은 거기서 막힌다.

원본에서 같은 `data-action` 을 공유하는 **형제** 요소가 둘 이상이면 선택지로 보고,
각 요소의 식별값(`data-*` 우선, 없으면 텍스트)을 모은다. 생성물에서는 그 값이
문서 어디에든 — 마크업이든 스크립트 배열이든 — 있는지만 본다. 한 화면에 다 보일
필요는 없다.

관측 (2026-10-01): 통과했던 자동 생성본이 은행 목록을 세 개만 만들고
`<!-- ... other banks ... -->` 로 끝냈다. 손수 제작한 Run 1·2·3 도 67개 중 9개만
가지고 있다.

보유 개수는 v3 에서도 그대로다 — `pick-bank` 를 Run 1·2·3 은 9개, Run 4 는 3개
가지고 있다. 바뀐 것은 I 가 세는 fatal 건수다. 검사 I 가 낱말 단위로 찾게 되면서
(4-1단계, `c35eb7a`·`b83d360`) Run 1·2·3 은 옛 검사기: I fatal 1건 / 현재: 3건이다
— `pick-bank` 외에 `quick` 의 `all` 과 `num` 의 `00` 이 더 잡힌다. Run 4 는 옛
검사기: 0건(검사 I 가 없었다) / 현재: 2건(`pick-bank` · `quick`)이다. 측정값은
`results/audit_*.v3.json`.

**설계 판단과 충돌할 수 있다.** 원본의 `quick` 선택지에는 `all`(전액)이 있는데,
`restructure-changelog.md` #15 는 "한 번 잘못 누르면 통장이 비는 버튼" 이라며
의도적으로 지웠다. 규칙은 그것도 fatal 로 센다 — 안전을 위한 제거와 귀찮아서
빠뜨린 것을 검사기가 스스로 가르지 않는다. 그래서 "빼도 되는 선택지" 는 연구자가
과제별로 `flows/allowed_removals.json` 에 이유와 함께 적고, 검사 I 는 거기 적힌 값만
fatal 에서 뺀다 (뺀 것은 `checks_stood_down` 에 남는다). 모델이 흐름 명세에 스스로 적은
`choices_removed` 는 판정에 쓰지 않는다 (11-6). 지금 그 파일은 비어 있다.

**선택지가 아닌 형제 무리도 있다.** 같은 `data-action` 의 형제 2개 이상이면 무엇이든
선택지로 세는 규칙은, 누르면 스크롤만 하는 표지판 · 탭도 센다. 공과금 원본의
`menu-chip`(60) · `menu-tab`(7) 이 그렇다 — 메뉴 항목을 찾아가는 수단이다. 그런
무리는 과제 파일의 `not_choices` 에 이유와 함께 선언하고, 검사 I 는 그 무리를 통째로
판정에서 뺀다 (지표 `choice_groups_not_choices`, 11-9). 값 몇 개를 허락하는
`allowed_removals` 와는 다른 선언이다.

## 검사기가 아직 못 잡는 것

### 상태 전이 누락

입력 수단은 올바르게 만들었으나, **그 입력이 다음 단계의 활성 조건에 연결되지
않아** 과제가 진행 불가능해진다.

관측 (2026-09-30, `outputs/restructure_auto/20260930-145811/attempt_3.html`):

```html
<input type="text" id="acc-number" placeholder="계좌번호 입력" data-action="input-account"/>
<button disabled data-action="go-amount">다음</button>
```

```js
document.getElementById('phone').addEventListener('click', function(e){
  ...
  } else if (a === 'input-account') {
    accountState.account = el.value;    // 클릭했을 때만 실행된다
    updateButtons();                    // 그래서 여기도 안 온다
  }
```

입력 칸은 제대로 있고 `placeholder` 도 맞다. 그런데 값 변화를 **클릭 이벤트로만**
받는다. `input` 리스너가 없으므로 사람이 타이핑해도 `updateButtons()` 가 불리지
않고 `다음` 의 `disabled` 가 풀리지 않는다. 화면에서 더 나아갈 수 없다.

**C(죽은 컨트롤)와 다르다.**

| | C 죽은 컨트롤 | 상태 전이 누락 |
|---|---|---|
| 증상 | 눌러도 아무 일이 없다 | **눌릴 수 없는 상태가 풀리지 않는다** |
| 원인 | `data-action` 에 대응하는 분기가 없다 | 입력과 활성 조건이 이어지지 않았다 |
| 요소 | 버튼 자체가 죽어 있다 | 버튼은 멀쩡하고 앞 단계가 신호를 안 보낸다 |
| 검사 | 정적으로 잡힌다 (마크업 vs 처리기) | 실제로 몰아 봐야 드러난다 |

지금은 A(과제 완주)의 `navigation failed` 로 간접적으로만 드러난다. 왜 멈췄는지는
Playwright 오류 문자열(`locator resolved to <button disabled ...>`)을 읽어야 안다.

**검사기에 넣는다면** — 과제가 멈춘 지점에서 대상 요소가 `disabled` 인지 보고,
그렇다면 그 활성 조건을 바꾸는 코드가 어떤 이벤트에 걸려 있는지 확인하는 방식이
가능하다. `click` 리스너만 있고 `input`/`change` 가 없는 폼 요소는 정적으로도
의심할 수 있다.
