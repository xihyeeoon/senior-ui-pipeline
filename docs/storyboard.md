# 화면설계서 (`python -m senior_ui.storyboard`)

**이 도구의 결과물은 화면설계서다.** 재구성 루프가 만드는 HTML 은 검사기가 걸어 보고
판정하기 위한 **검증용 속 재료**이고, 디자이너가 받아 보는 것은 그 HTML 에서 뽑은
설계서다. 화면마다 화면 ID, 회색 와이어프레임 그림, 그림 위의 번호 영역, 오른쪽 설명
표(영역별 요소 · 누르면 가는 곳 · 조건별 상태)가 한 장(가로 A4)에 있다. 색 · 모양은
디자이너의 몫이라 설계서에 넣지 않는다 — 그림은 회색조이고 사진 · 아이콘 자리는 X 상자다.

원칙 셋:

1. **검사를 통과한 HTML 에서만 뽑는다.** 통과하지 못한 실행 · 막혀 멈춘 실행(`stuck`) ·
   최종 검사 결과가 통과가 아닌 실행은 만들지 않고 이유를 찍는다 (종료 2).
2. **"누르면 어디로 가는가" 는 도구가 실제로 눌러서 확인한 것만 적는다.** 모델의 말
   (계획 · 흐름 명세 · 영역 설명)을 믿지 않는다.
3. **모델은 영역 묶기와 설명 문장만 쓴다.** 재구성 · 검사 · 고르기는 바꾸지 않는다 —
   설계서는 실행이 끝난 뒤 실행 폴더를 읽기만 해서 만든다. 실행 폴더의 원래 파일은 한
   바이트도 고치지 않는다 (시험이 해시로 본다).

## 명령

```powershell
# 실제 - 영역 묶기에 모델 호출 한 번 (어긋나면 한 번 더)
.\.venv\Scripts\python.exe -m senior_ui.storyboard outputs\restructure_auto\<실행> --model gpt-6.1-sol

# API 없이 - 정해진 영역 답
.\.venv\Scripts\python.exe -m senior_ui.storyboard outputs\restructure_auto\<실행> --mock
```

| 인자 | |
|---|---|
| `--model 이름` | 영역 묶기 모델. 주지 않으면 `config.DEFAULT_MODEL` (지금 `gpt-6.1-sol`). 키는 재구성 루프와 같이 환경 변수 또는 `.envs` 의 `OPENAI_API_KEY` |
| `--mock` | 모델을 부르지 않고 정해진 답을 쓴다 (키도 읽지 않는다). 시험용 모드 `bad-then-good` · `bad` 가 더 있다 |
| `--reasoning-effort` | 추론형 모델의 노력. 주지 않으면 `config.DEFAULT_REASONING_EFFORT` (`medium`) |
| `--port N` | 서버 포트. 주지 않으면 빈 포트에 제 서버를 띄우고 끝에서 제 것만 끈다 |
| `--no-pdf` | PDF 를 만들지 않는다 |
| `--concurrency N` | 동시에 여는 확인 페이지 수 (기본 8) |

종료 코드: `0` = 만들었다, `1` = 만들었지만 영역 묶기 모델을 부르지 못해 화면마다 "기타"
하나로 묶었다 (이유는 맨 앞장과 `storyboard.json` 의 `regions_call.error`), `2` = 만들지
않았다 (통과하지 못한 실행 · 실행 폴더가 아님 · 저장소 밖 · 서버 · 브라우저).

## 설계서의 각 칸이 어디서 오는가

| 칸 | 출처 | 어떻게 |
|---|---|---|
| 화면 ID `scr-<화면 이름>` | 도구 확인 | 그 상태에서 실제로 켜진 화면(`.screen.on` 의 `data-screen`) |
| 와이어프레임 그림 | 도구 확인 | `wireframe.html` 을 흐름 명세대로 걸어 찍었다 |
| 요소 번호 · 글자 · aria-label · 위치 | 도구 확인 | 그 상태에서 보이는 `data-action` 요소 (덮개 아래에 깔린 것은 빼고 수만 적는다) |
| **요소와 동작** ("선택 시 [scr-amount] 로 이동") | **도구 확인** | 요소마다 새 페이지에서 그 상태까지 다시 걸은 뒤 원래 빌드를 눌러 보았다 |
| 선택지 무리 ("38개 중 하나 선택") | 도구 확인 | 무리는 최종 검사의 `choice_groups_original` (검사 I 가 세는 것). 대표 하나만 누른다 |
| 과제 밖 입구 표시 | 도구 확인 | `data-action` 이 `oos-` 로 시작 (검사 K 와 같은 규칙). 누른 결과는 그대로 적는다 |
| 조건별 화면과 그 조건 | 흐름 명세 · 과제 | `error_paths`(오류) · `reveal`(펼친 뒤) · `steps` 의 두 번째 방문. 오류의 뜻은 과제의 원본 흐름(`about` · `uses`) |
| **영역 이름 · 설명** | **모델 설명** | 모델이 그림 · 요소 목록 · 화면 목적으로 묶었다. `--mock` 이면 "mock", 모델이 빠뜨린 요소를 도구가 모으면 "도구 묶음" |
| 화면 목적 · 원본 화면 | 계획 (재구성 실행의 모델) | 실행의 계획 파일을 그대로 옮긴다 |
| 변경 목록 · 진단 요약 | 계획 · 진단 (재구성 실행의 모델) | 그대로 옮긴다 |
| 화면 순서 | 흐름 명세 + 도구 확인 | 흐름 명세의 걸음을 그 상태의 요소 번호로 적는다 ("앞 화면에서 e7 '이체하기' 누름") |
| 실행 정보 | `summary.json` · git | 실행 id · 모델 · 커밋 · 원본 지문(실행 커밋의 원본 파일, 줄끝을 LF 로 맞춘 sha256) |

설계서의 각 장에도 칸마다 출처 꼬리표가 붙는다 — 동작 칸은 "도구 확인", 이름 · 설명 칸은
"모델 설명" / "mock" / "도구 묶음".

## 어떻게 만드는가

### 1. 상태와 다시 걷는 법

흐름 명세에서 상태를 뽑는다 (`walk.states_of`). 상태 하나가 설계서의 그림 한 장이다.

| 상태 | 다시 걷는 법 | 장 |
|---|---|---|
| 정답 경로의 방문 | `steps` 를 그 방문까지 | 화면마다 처음 지나는 것이 **본 장** |
| 같은 화면의 두 번째 방문 | `steps` 를 그 방문까지 | 조건별 장 (`scr-x--visit-2`) |
| 오류 경로 | `from_step` 까지 정답대로 → `inputs` → `expect_screen` 이 켜지기를 기다림 | 조건별 장 (`scr-x--error-<id>`) |
| 펼치기 | `at` 까지 → `do` 의 조작 | 조건별 장 (`scr-x--reveal-<action>`) |

걸음은 검사기의 함수(`audit.drive.run_actions` · `settle`)로 밟는다 — 검사기가 통과시킨 그
걸음이다. 정답 경로가 지나지 않는 화면(오류만 보이는 화면)은 그 화면에 처음 닿은 조건별
상태가 본 장이 된다.

### 2. 그림 — 회색 덮개 사본에서

`wireframe.html` 을 열고 그 상태까지 걷는다. 덮개는 문서 전체를 회색조로 바꾸고
(`html { filter: grayscale(1) }`), `img · svg · video · canvas · [role=img]` 와 배경 그림을
쓴 요소를 X 표시 상자로 바꾼다. 스크롤되는 화면은 켜진 화면 안의 스크롤 요소가 넘치는
만큼 `#phone` 을 늘려 한 장으로 찍는다 — 아래에 고정된 버튼은 늘어난 화면의 맨 아래에
온다. 늘려도 줄지 않는 목록(높이를 못박은 것)은 그 높이 제한을 푼다. `#phone` 은
8,000px 까지 늘린다 (2배 해상도 그림이 Chromium 의 한 장 한도 16,384px 안에 들게). 넘는
높이는 잘린 채 찍고 장에 "아래 Npx 는 다 찍지 못함" 으로 적는다 — 공과금의 메뉴를 다
펼친 상태가 그렇다 (22,000px 남짓).

덮개는 스타일만 바꾸고 `data-action` 요소를 더하거나 빼지 않는다. 그래서 그림 페이지에서
모은 요소의 순번(문서 안의 `[data-action]` 순서)으로 확인 페이지의 같은 요소를 찾는다.

### 3. 요소와 번호

그 상태에서 보이는 `data-action` 요소를 모은다 — 그려져 있고(display · visibility · 조상의
opacity), `#phone` 과 겹치고, 가운데를 찍었을 때 그 요소(또는 그 안)가 맞는 것. 위에서
아래, 같은 줄(위쪽 끝 6px 안)이면 왼쪽부터 `e1, e2 …`.

선택지 무리는 그 상태에서 둘 이상 보이면 항목 하나로 묶는다 ("pick-bank 무리 38개").
무리는 **최종 검사의 `choice_groups_original`** — 검사 I 가 세는 것, 원본에서 무리였던
`data-action` 이름(과제가 선택지가 아니라고 선언한 `not_choices` 는 빠져 있다)이다. 대표는
읽는 순서의 첫 것이다 (꺼진 것은 뒤로).

### 4. 눌러 보기 — 원래 빌드에서

항목마다 새 페이지(새 브라우저 문맥)에서 그 상태까지 다시 걸은 뒤, **실행 폴더의 최종
HTML 그대로** 를 누른다. 꺼져 있으면 누르지 않고 "꺼져 있음" 이다. 누른 뒤 1.2초 동안 다른
화면이 켜지는지 보고 (조회를 흉내 내느라 늦게 넘어가는 설계가 있다), 켜지지 않으면 같은
화면에서 무엇이 바뀌었는지 본다.

| 결과 | 설계서의 말 |
|---|---|
| 켜진 화면이 바뀌었다 | 선택 시 [scr-…] 로 이동 |
| 같은 화면에서 새 글이 보였다 · 글이 사라졌다 · 입력 칸 값 · 알림창 · 글의 순서 · 표시 상태(클래스 · aria) · 스크롤 | 선택 시 같은 화면에서 바뀜 — 새로 보임: '…' (첫 줄만, 나머지는 "외 n줄") |
| 아무것도 바뀌지 않았다 | 선택해도 바뀌는 것 없음 |
| 꺼져 있다 | 꺼져 있음 (이 상태에서는 누를 수 없음) |
| 누르지 못했다 · 다시 걷지 못했다 | 확인 못 함 — 이유 |

설계서의 페이지는 **시각과 난수를 고정한다** (`clock.set_fixed_time` · 씨앗을 넣은
`Math.random`). 상태 표시줄의 시계가 누르는 사이에 분을 넘기면 "아무 일 없음" 이 "새로
보임: '1:40'" 으로 적히고, 비밀번호 숫자판처럼 그릴 때마다 섞는 목록은 그림 페이지와 확인
페이지의 순서가 달라진다. 타이머는 그대로 돈다 — 늦게 넘어가는 전환은 그대로 본다.

확인 페이지는 동시에 8개까지 연다. 이체 실행 하나에 항목 85~91개 · 1분 남짓, 공과금은
항목 404개 · 3분 남짓이었다 (아래 "시간").

### 5. 영역 묶기 — 모델 호출 한 번

넣는 것은 셋뿐이다 — 장마다 요소 번호를 얹은 와이어프레임 그림, 요소 목록(번호 · 세로
위치 · 글자 · aria-label · 도구가 확인한 동작), 계획의 화면 목적. 고령자 UX 규칙이나 평가는
넣지 않는다 — 이 호출은 설명만 쓴다. 누르면 어디로 가는지는 쓰지 말라고 한다.

받는 것 (JSON):

```json
{"sheets": [{"id": "scr-home", "regions": [
  {"no": 1, "name": "상단 바", "elements": ["e1", "e2"], "description": "한두 줄"}]}]}
```

검사 (`regions.check`): 장마다 모든 요소가 정확히 한 영역에 들어갔는가, 없는 번호 · 없는
장을 쓰지 않았는가, 이름 없는 영역은 없는가. 어긋나면 문제를 적어 **한 번 다시 묻는다**
(그림은 다시 보내지 않는다). 그래도 어긋나면 맞는 부분은 쓰고, 남은 요소를 "기타" 영역으로
묶고, `regions_call.fallback` 에 장마다 기타로 모은 요소와 버린 번호를 남긴다. 영역 번호는
도구가 위에서 아래로 다시 매긴다.

`--mock` 의 정해진 답은 요소를 위에서 아래로 보며 세로로 24px 넘게 벌어지는 곳에서 나눈다
("영역 n", 설명은 묶은 번호).

### 6. 그리기

`storyboard.json` 하나로 그린다 (`render.render`). 긴 그림은 한 장에 들도록 여러 단으로
잘라 나란히 놓는다 (가장 크게 보이는 단 수, 배율은 1 이하). 영역 테두리(굵게, 번호)와 요소
테두리(점선, `e` 번호)는 HTML 로 얹으므로 PDF 를 확대하면 선과 번호가 선명하다. 표가 한
장을 넘으면 인쇄에서 다음 쪽으로 이어진다.

## storyboard.json

| 키 | |
|---|---|
| `run` | 실행 id · 과제 · 생성 모델 · 최종 빌드(시도 · 다듬기 회차) · 검사 단계 · 커밋 · dirty · 원본 지문 · 생성 비용 |
| `task` | 과제 id · 이름 · 설명 (과제 파일) |
| `flow` | `steps` (걸음마다 장 · 앞 장에서 한 조작) · `errors` (오류마다 조건 · 넣는 곳 · 나오는 장 · 되돌아가기) · `reveals` |
| `changes` · `diagnosis` | 계획의 변경(대응 진단의 문제 글까지) · 진단 (수 · 근거 종류 · 화면별 · 목록) |
| `choice_groups` | 무리로 묶은 이름 (최종 검사의 `choice_groups_original`) |
| `counts` | 장 · 본 장 · 항목 · 요소 · 누르기 수 |
| `sheets[]` | 장마다 `id` · `screen` · `kind` · `main` · `of` · `condition` · `purpose` · `picture` · `size` · `grown` · `clipped` · `covered` · `items[]` (`no` · `kind` · `action` · `text` · `aria` · `box` · `disabled` · `entrance` · `group` · `result`) · `regions[]` (`no` · `name` · `description` · `elements` · `box` · `source`) · `conditions` |
| `regions_call` | 영역 묶기 호출 — 모델 · mock · 호출마다(첫 · 다시) 그림 수 · 토큰 어림 · 실측 토큰 · 비용 · 걸린 시간 · 문제 · 파일, 전체 비용, `fallback`, `error` |
| `generated` | 만든 시각 · 도구 커밋 · 그림/누르기/전체 걸린 시간 |

## 한계

- **눌러 본 것은 그 상태의 한 번이다.** 같은 버튼이 입력값에 따라 다르게 가는 설계(예: 맞는
  계좌면 다음, 틀리면 오류)는 흐름 명세가 적은 상태에서 누른 결과만 적힌다 — 다른 갈래는
  오류 경로 · 펼치기의 조건별 장으로만 보인다.
- **선택지 무리는 대표 하나만 누른다.** 나머지가 같은 곳으로 간다는 것은 확인하지 않았다.
- **1.2초보다 늦게 넘어가는 화면 전환은 "같은 화면에서 바뀜" 으로 적힌다.**
- **덮개 아래에 깔린 요소는 뺀다** (수만 적는다). 모달이 떠 있는 상태의 뒤 화면 버튼이 그렇다.
- **8,000px 넘는 화면은 잘린다.** 잘린 아래쪽 요소는 그 장의 요소에 들어가지 않는다.
- **글자로 된 아이콘(☺ ⌕ 같은 기호)은 X 상자로 바뀌지 않는다** — 글자이기 때문이다.
