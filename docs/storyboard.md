# 화면설계서 (`python -m senior_ui.storyboard`)

**이 도구의 결과물은 화면설계서다.** 재구성 루프가 만드는 HTML 은 검사기가 걸어 보고
판정하기 위한 **검증용 속 재료**이고, 디자이너가 받아 보는 것은 그 HTML 에서 뽑은
설계서다. 실무 와이어프레임 관례를 따른다 (11-12b):

- **맨 앞장** — 과제 · 화면 순서 · 오류 경로 · 변경 목록 · 진단 요약 · 실행 정보 · 칸마다의 출처
- **와이어플로** — 모든 화면을 작은 그림으로 한 장에 늘어놓고 정답 경로를 번호 붙은 화살표로,
  오류 경로를 점선 갈래와 되돌아가는 화살표로, 펼치기를 점선으로 잇는다. 화살표 옆에 누른 것
- **기능-화면 표** — 기능(과제 단계 · 선택지 무리 · 입력 수단 · 오류 회복 · 과제 밖 입구) × 화면.
  "기능은 줄이지 않는다" 의 확인표
- **화면마다 한 장** — 맨 위 정보칸 한 줄(화면 ID · 화면 이름 · 경로 · 바탕이 된 원본 화면 ·
  조건), 왼쪽은 로우파이 와이어프레임 그림 위의 번호 영역, 오른쪽은 설명 표(영역별 요소 ·
  클릭 결과 주석 · 예외). 조건별 화면(오류 상태 · 펼친 뒤 · 다시 지남)은 그 화면 뒤에 오고 장
  제목에 [오류] · [펼침] · [다시 지남] 꼬리표가 붙는다

색 · 모양은 디자이너의 몫이라 설계서에 넣지 않는다 — 그림은 회색 상자와 글자뿐이고 사진 ·
아이콘 · 로고 자리는 X 상자다. **위치 · 크기 · 글자 크기 · 굵기는 그대로 둔다 — 위계와 크기는
설계 결정이므로 남긴다.**

원칙 셋:

1. **검사를 통과한 HTML 에서만 뽑는다.** 통과하지 못한 실행 · 막혀 멈춘 실행(`stuck`) ·
   최종 검사 결과가 통과가 아닌 실행은 만들지 않고 이유를 찍는다 (종료 2).
2. **"누르면 어디로 가는가" 는 도구가 실제로 눌러서 확인한 것만 적는다.** 모델의 말
   (계획 · 흐름 명세 · 영역 설명)을 믿지 않는다.
3. **모델은 영역 묶기와 설명 문장만 쓴다.** 재구성 · 검사 · 고르기는 바꾸지 않는다 —
   설계서는 실행이 끝난 뒤 실행 폴더를 읽기만 해서 만든다. 실행 폴더의 원래 파일은 한
   바이트도 고치지 않는다 (시험이 해시로 본다).

## 명령

```powershell
# 실제 - 영역 묶기에 모델 호출 한 번 (어긋나면 한 번 더)
.\.venv\Scripts\python.exe -m senior_ui.storyboard outputs\restructure_auto\<실행> --model gpt-6.1-sol

# API 없이 - 정해진 영역 답
.\.venv\Scripts\python.exe -m senior_ui.storyboard outputs\restructure_auto\<실행> --mock

# API 없이 - 이미 만든 설계서의 영역 답을 그대로 (새 형식으로 다시 뽑기)
.\.venv\Scripts\python.exe -m senior_ui.storyboard outputs\restructure_auto\<실행> `
    --regions-from outputs\restructure_auto\<실행>\storyboard\storyboard.json
```

| 인자 | |
|---|---|
| `--model 이름` | 영역 묶기 모델. 주지 않으면 `config.DEFAULT_MODEL` (지금 `gpt-6.1-sol`). 키는 재구성 루프와 같이 환경 변수 또는 `.envs` 의 `OPENAI_API_KEY` |
| `--mock` | 모델을 부르지 않고 정해진 답을 쓴다 (키도 읽지 않는다). 시험용 모드 `bad-then-good` · `bad` 가 더 있다 |
| `--regions-from 파일` | 저장된 설계서(`storyboard.json`)의 영역 답을 그대로 쓴다 — 모델을 부르지 않는다 (키도 읽지 않는다). 요소 번호가 이번 걷기와 같을 때만 (아래 "다시 그리기"). `--model` · `--mock` 과 같이 쓸 수 없다 |
| `--reasoning-effort` | 추론형 모델의 노력. 주지 않으면 `config.DEFAULT_REASONING_EFFORT` (`medium`) |
| `--port N` | 서버 포트. 주지 않으면 빈 포트에 제 서버를 띄우고 끝에서 제 것만 끈다 |
| `--no-pdf` | PDF 를 만들지 않는다 |
| `--concurrency N` | 동시에 여는 확인 페이지 수 (기본 8) |

종료 코드: `0` = 만들었다, `1` = 만들었지만 영역 묶기 모델을 부르지 못해 화면마다 "기타"
하나로 묶었다 (이유는 맨 앞장과 `storyboard.json` 의 `regions_call.error`), `2` = 만들지
않았다 (통과하지 못한 실행 · 실행 폴더가 아님 · 저장소 밖 · `--regions-from` 의 요소 번호가
다름 · 서버 · 브라우저).

| `shots/<상태>.marked.png` | 요소 번호를 얹은 그림 (1배) — 영역 묶기 호출에 보낸 것 |
| `wireframe.html` | 그림용 사본 — 최종 HTML 에 로우파이 덮개(스타일과, 찍기 직전에 그것을 켜는 스크립트)만 넣었다 |
| `regions.prompt.txt` · `regions.response.txt` | 영역 묶기 호출의 프롬프트(그림은 파일 · 크기 · 토큰 어림 줄로)와 답 원문. 다시 물었으면 `regions.retry.*` |
| `regions.from.json` | `--regions-from` 으로 읽은 저장된 설계서의 사본 (그 파일이 이 폴더 안에 있었어도 남는다 — 지우기 전에 읽는다) |
| `storyboard.log` | 한 줄씩 무엇을 했는지 (서버 · 그림 · 누르기 · 호출) |

## 설계서의 각 칸이 어디서 오는가

| 칸 | 출처 | 어떻게 |
|---|---|---|
| 화면 ID `scr-<화면 이름>` | 도구 확인 | 그 상태에서 실제로 켜진 화면(`.screen.on` 의 `data-screen`) |
| 화면 이름 | 모델 설명 / 계획 | 영역 묶기 답의 장마다 `name` (그 장, 없으면 본 장의 것). 없으면 계획의 화면 목적 첫 문장을 20자에서 자른 것 (`--mock` 은 늘 이쪽) |
| 경로 | 흐름 명세 + 도구 확인 | 정답 걸음을 그 상태의 방문까지 걸은 장들 (`홈 > 받는 사람 > 계좌 입력`), 조건별 장은 끝에 제 장 |
| 바탕이 된 원본 화면 | 계획 | 계획의 `screens[].from` |
| 와이어프레임 그림 | 도구 확인 | `wireframe.html` 을 흐름 명세대로 걸어 덮개를 켜고 찍었다 |
| 요소 번호 · 글자 · aria-label · 위치 | 도구 확인 | 그 상태에서 보이는 `data-action` 요소 (덮개 아래에 깔린 것은 빼고 수만 적는다) |
| **요소와 동작** ("클릭 시 → [scr-amount] 이동") | **도구 확인** | 요소마다 새 페이지에서 그 상태까지 다시 걸은 뒤 원래 빌드를 눌러 보았다 |
| 선택지 무리 ("38개 중 하나 선택 → [scr-account] 이동") | 도구 확인 | 무리는 최종 검사의 `choice_groups_original` (검사 I 가 세는 것). 대표 하나만 누른다 |
| 예외: 비활성 | 도구 확인 | 눌러 보려 했을 때 꺼져 있던 요소 |
| 예외: 빈 화면 | 모델 설명 | 영역 묶기 답이 그 영역에 `empty_state: true` 를 붙였을 때만 — 표시 옆에 "모델 설명" 꼬리표. 글자로 판정하지 않는다 |
| 와이어플로의 화살표 | 흐름 명세 + 도구 확인 | 정답 경로의 걸음 · 오류 경로(와 되돌아가기) · 펼치기만. 이어지는 장은 도구가 그 상태까지 걸어 확인한 화면. 화살표 옆의 누른 것은 그 걸음의 조작을 앞 장의 요소 번호로 |
| 기능-화면 표의 표시 | 도구 확인 | 장마다 보인 data-action 요소의 값(선택지 · 숫자판 — 원본의 값으로) · 이름(입구 · 입력 칸) · 흐름 명세의 걸음 · 오류 경로 (아래 "기능-화면 표") |
| 과제 밖 입구 표시 | 도구 확인 | `data-action` 이 `oos-` 로 시작 (검사 K 와 같은 규칙). 누른 결과는 그대로 적는다 |
| 조건별 화면과 그 조건 | 흐름 명세 · 과제 | `error_paths`(오류) · `reveal`(펼친 뒤) · `steps` 의 두 번째 방문. 오류의 뜻은 과제의 원본 흐름(`about` · `uses`) |
| **영역 이름 · 설명** | **모델 설명** | 모델이 그림 · 요소 목록 · 화면 목적으로 묶었다. `--mock` 이면 "mock", 모델이 빠뜨린 요소를 도구가 모으면 "도구 묶음" |
| 화면 목적 · 원본 화면 | 계획 (재구성 실행의 모델) | 실행의 계획 파일을 그대로 옮긴다 |
| 변경 목록 · 진단 요약 | 계획 · 진단 (재구성 실행의 모델) | 그대로 옮긴다 |
| 화면 순서 | 흐름 명세 + 도구 확인 | 흐름 명세의 걸음을 그 상태의 요소 번호로 적는다 ("앞 화면에서 e7 '이체하기' 누름") |
| 실행 정보 | `summary.json` · git | 실행 id · 모델 · 커밋 · 원본 지문(실행 커밋의 원본 파일, 줄끝을 LF 로 맞춘 sha256) |

설계서의 각 장에도 칸마다 출처 꼬리표가 붙는다 — 동작 칸은 "도구 확인", 이름 · 설명 칸은
"모델 설명" / "mock" / "도구 묶음", 화면 이름이 계획에서 왔으면 "계획의 화면 목적 앞부분".

## 어떻게 만드는가

### 1. 상태와 다시 걷는 법

흐름 명세에서 상태를 뽑는다 (`walk.states_of`). 상태 하나가 설계서의 그림 한 장이다.

| 상태 | 다시 걷는 법 | 장 |
|---|---|---|
| 정답 경로의 방문 | `steps` 를 그 방문까지 | 화면마다 처음 지나는 것이 **본 장** |
| 같은 화면의 두 번째 방문 | `steps` 를 그 방문까지 | 조건별 장 (`scr-x--visit-2`) |
| 오류 경로 | `from_step` 까지 정답대로 → `inputs` → `expect_screen` 이 켜지기를 기다림 | 조건별 장 (`scr-x--error-<id>`) |
| 펼치기 | `at` 까지 → `do` 의 조작 | 조건별 장 (`scr-x--reveal-<action>`) |

걸음은 검사기의 함수(`audit.drive.run_actions` · `settle`)로 밟는다 — 검사기가 통과시킨 그
걸음이다. 정답 경로가 지나지 않는 화면(오류만 보이는 화면)은 그 화면에 처음 닿은 조건별
상태가 본 장이 된다.

### 2. 그림 — 로우파이 덮개 사본에서

`wireframe.html` 을 열고 그 상태까지 걷는다 — 걷는 동안의 페이지는 원래 스타일 그대로다.
그림을 찍기 직전에 `__sbWire()` 가 원래 스타일을 읽어 표시를 붙인 뒤 덮개(`html.sb-wire`
아래의 규칙)를 켠다. 무엇이 상자였는지는 지우기 전의 배경 · 그림자 · 테두리로만 알 수 있어서다.

| 원래 디자인 | 덮개를 켠 뒤 |
|---|---|
| 배경 · 채우기 · 그림자 · 그라데이션 · 둥근 모서리 · 글자 그림자 | 없앤다. 불투명 바탕은 흰 종이(뒤에 깔린 화면을 가린다), 화면을 덮는 반투명 막(모달 뒤)은 옅은 흰 막 |
| 글자 색 (자리표시 글 포함) | 진회색 `#333` 하나 |
| 누를 수 있는 요소(`data-action`) · 입력 칸 | 1px 회색 테두리 상자 (꺼진 것은 점선) |
| 묶음 상자 — 바탕색이 뒤와 다르거나, 그림자가 있거나, 네 변에 테두리가 있던 것 | 1px 회색 테두리 상자 (화면 전체 바탕 · `#phone` · `.screen` 은 빼고) |
| 그 밖의 테두리 (한 변 구분선 등) | 두께는 두고 색만 지운다 |
| `img · svg · video · canvas · [role=img]` · 배경 그림 · 가면 그림(mask)을 쓴 요소 | X 가 그어진 회색 상자 |

위치 · 크기 · 글자 크기 · 굵기는 그대로 둔다 — 위계와 크기는 설계 결정이므로 남긴다. 그래서
덮개는 배치를 바꾸는 속성(크기 · 여백 · 테두리 두께 · 글꼴)을 하나도 쓰지 않고, 상자는
`outline` 으로 그린다 (시험이 덮개를 켜기 전후의 위치 · 크기 · 글자 크기 · 굵기를 견준다).
덮개의 표시(`data-sb-*`)는 요소의 값으로 읽지 않는다. 스크롤되는 화면은 켜진 화면 안의 스크롤 요소가 넘치는
만큼 `#phone` 을 늘려 한 장으로 찍는다 — 아래에 고정된 버튼은 늘어난 화면의 맨 아래에
온다. 늘려도 줄지 않는 목록(높이를 못박은 것)은 그 높이 제한을 푼다. `#phone` 은
8,000px 까지 늘린다 (2배 해상도 그림이 Chromium 의 한 장 한도 16,384px 안에 들게). 넘는
높이는 잘린 채 찍고 장에 "아래 Npx 는 다 찍지 못함" 으로 적는다 — 공과금의 메뉴를 다
펼친 상태가 그렇다 (22,000px 남짓).

덮개는 스타일만 바꾸고 `data-action` 요소를 더하거나 빼지 않는다. 그래서 그림 페이지에서
모은 요소의 순번(문서 안의 `[data-action]` 순서)으로 확인 페이지의 같은 요소를 찾는다.

### 3. 요소와 번호

그 상태에서 보이는 `data-action` 요소를 모은다 — 그려져 있고(display · visibility · 조상의
opacity), `#phone` 과 겹치고, 가운데를 찍었을 때 그 요소(또는 그 안)가 맞는 것. 위에서
아래, 같은 줄(위쪽 끝 6px 안)이면 왼쪽부터 `e1, e2 …`.

선택지 무리는 그 상태에서 둘 이상 보이면 항목 하나로 묶는다 ("pick-bank 무리 38개").
무리는 **최종 검사의 `choice_groups_original`** — 검사 I 가 세는 것, 원본에서 무리였던
`data-action` 이름(과제가 선택지가 아니라고 선언한 `not_choices` 는 빠져 있다)이다. 대표는
읽는 순서의 첫 것이다 (꺼진 것은 뒤로).

### 4. 눌러 보기 — 원래 빌드에서

항목마다 새 페이지(새 브라우저 문맥)에서 그 상태까지 다시 걸은 뒤, **실행 폴더의 최종
HTML 그대로** 를 누른다. 꺼져 있으면 누르지 않고 "꺼져 있음" 이다. 누른 뒤 1.2초 동안 다른
화면이 켜지는지 보고 (조회를 흉내 내느라 늦게 넘어가는 설계가 있다), 켜지지 않으면 같은
화면에서 무엇이 바뀌었는지 본다.

| 결과 | 설계서의 말 |
|---|---|
| 켜진 화면이 바뀌었다 | 클릭 시 → [scr-…] 이동 |
| 같은 화면에서 새 글이 보였다 | 클릭 시 → 같은 화면에서 '…' 나타남 (첫 줄만, 나머지는 "외 n줄") |
| 글이 사라졌다 · 입력 칸 값 · 알림창 | 클릭 시 → 같은 화면에서 '…' 사라짐 · 입력 칸에 '…' · 알림창 '…' 뜸 |
| 글의 순서 · 표시 상태(클래스 · aria) · 스크롤 | 클릭 시 → 같은 화면에서 글의 순서 / 표시 상태 (글은 그대로) / 스크롤 위치가 바뀜 |
| 아무것도 바뀌지 않았다 | 클릭해도 변화 없음 |
| 꺼져 있다 | 비활성 (이 상태에서는 누를 수 없음) — 설명 표에 "예외: 비활성" |
| 선택지 무리 | 38개 중 하나 선택 → [scr-account] 이동 (눌러 본 대표: '경남') |
| 누르지 못했다 · 다시 걷지 못했다 | 확인 못 함 — 이유 |

걷기가 남기는 결과(`result` 의 `detail`)는 그대로이고, 주석 꼴은 그리는 쪽(`render.result_text` ·
`same_phrase`)이 조각마다 옮긴다.

설계서의 페이지는 **시각과 난수를 고정한다** (`clock.set_fixed_time` · 씨앗을 넣은
`Math.random`). 상태 표시줄의 시계가 누르는 사이에 분을 넘기면 "아무 일 없음" 이 "새로
보임: '1:40'" 으로 적히고, 비밀번호 숫자판처럼 그릴 때마다 섞는 목록은 그림 페이지와 확인
페이지의 순서가 달라진다. 타이머는 그대로 돈다 — 늦게 넘어가는 전환은 그대로 본다.

확인 페이지는 동시에 8개까지 연다. 이체 실행 하나에 항목 85~91개 · 1분 남짓, 공과금은
항목 404개 · 3분 남짓이었다 (아래 "시간").

### 5. 영역 묶기 — 모델 호출 한 번

넣는 것은 셋뿐이다 — 장마다 요소 번호를 얹은 와이어프레임 그림, 요소 목록(번호 · 세로
위치 · 글자 · aria-label · 도구가 확인한 동작), 계획의 화면 목적. 고령자 UX 규칙이나 평가는
넣지 않는다 — 이 호출은 설명만 쓴다. 누르면 어디로 가는지는 쓰지 말라고 한다.

받는 것 (JSON):

```json
{"sheets": [{"id": "scr-home", "name": "이체 시작", "regions": [
  {"no": 1, "name": "상단 바", "elements": ["e1", "e2"], "description": "한두 줄"},
  {"no": 2, "name": "빈 목록", "elements": ["e3"], "description": "…", "empty_state": true}]}]}
```

장의 `name`(화면 이름)과 영역의 `empty_state`(빈 상태 안내)는 없어도 맞는 답이다 (11-12b).
화면 이름은 글이 아니거나 40자를 넘으면 버린다.

검사 (`regions.check`): 장마다 모든 요소가 정확히 한 영역에 들어갔는가, 없는 번호 · 없는
장을 쓰지 않았는가, 이름 없는 영역은 없는가. 어긋나면 문제를 적어 **한 번 다시 묻는다**
(그림은 다시 보내지 않는다). 그래도 어긋나면 맞는 부분은 쓰고, 남은 요소를 "기타" 영역으로
묶고, `regions_call.fallback` 에 장마다 기타로 모은 요소와 버린 번호를 남긴다. 영역 번호는
도구가 위에서 아래로 다시 매긴다.

`--mock` 의 정해진 답은 요소를 위에서 아래로 보며 세로로 24px 넘게 벌어지는 곳에서 나눈다
("영역 n", 설명은 묶은 번호).

### 6. 와이어플로

`storyboard.json` 의 `flow` 만으로 그린다 (`render.flow_graph` · `flow_pages` ·
`render_flow_page`). 마디는 정답 경로의 걸음마다의 장(번호 ①②…)과, 그 출발 걸음 아래 갈래
줄의 오류 장 · 펼친 뒤 장이다. 작은 그림은 폰 한 화면 비율로 위쪽만 보이고, 더 긴 화면은
"↓ 길이 Npx" 를 붙인다.

| 잇기 | 선 | 옆에 적는 것 |
|---|---|---|
| 걸음 → 다음 걸음 | 실선 · 번호 | 앞 화면에서 누른 것 (`e7 '이체하기'`, 조작이 셋 이상이면 처음 … 끝) |
| 걸음 → 오류 장 | 빨간 점선 | 오류 id · 넣은 것 |
| 오류 장 → 되돌아가는 장 | 빨간 점선 ↩ | 되돌리는 조작 |
| 걸음 → 펼친 뒤 장 | 보라 점선 | 펼치는 조작 |

한 줄에 걸음 8개까지 (넘으면 다음 띠, 띠를 넘는 화살표는 오른쪽으로 나가 띠 사이로 돌아
들어온다). 한 장에 들도록 그림 폭을 정하고, 60px 보다 작아져야 하면 띠마다 장을 나눈다
(장을 넘는 화살표는 "다음 장 n" · "앞 장 n 에서" 글로). 저장된 이체 답은 한 줄과 오류
갈래 둘, 공과금 답은 두 띠와 펼침 갈래 다섯으로 한 장에 든다. 도구가 눌러 본 다른 결과
(어느 버튼이 다른 화면으로 감)로는 화살표를 만들지 않는다 — 그것은 각 장의 설명 표에 있다.

### 7. 기능-화면 표

"기능은 줄이지 않는다" 의 확인표 (`features.py`). 줄은 기능, 칸은 본 장의 화면 ID, 표시는 그
기능이 그 화면의 어느 장에서 보였는가 — **●** 흐름이 머무는 상태(본 장 · 다시 지나는 장)에서
보임, **○** 조건별 장(펼친 뒤 · 오류)에서만 보임. 오류 회복 줄만은 그 오류가 보이는 화면에
● 다. 표시가 하나도 없는 줄은 "보지 못함" 으로 남고 `features.missing` 과 로그 한 줄에 적힌다.

**선택지 무리 · 숫자판은 이름이 아니라 값으로 찾는다** (11-12c). 원본의 무리마다 원본을 걸으며
모은 값 목록(아래 "원본 걷기")을, 장마다 그 상태의 누를 수 있는 요소 — data-action 이 무엇이든
— 의 값에서 검사 I 와 같은 경계 규칙(`i_choices.present`: 한글은 뒤에 말이 붙어도, 숫자 ·
영문은 앞뒤가 떨어져야 같은 값)으로 찾는다. 요소의 값은 검사 I 가 모으는 것과 같다 —
data-action 말고 첫 `data-*` 값, 없으면 글자. 보이는 글자 전체로는 찾지 않는다 ("1만원" 이라고
쓴 빠른 금액 단추의 값은 10000 이지 숫자판의 1 이 아니다). 줄에는 원본 값 수 · 찾은 값 수
("값 38/67 찾음") · 빌드가 쓴 data-action 이름을, 칸에는 그 화면의 장 하나에서 찾은 가장 많은
수("38/67", ● 칸에서 조건별 장이 더 많이 보이면 "○n")를 적는다. 어디서도 못 찾으면 "보지 못함
(값 0/67)". 원본의 값을 모으지 못했으면(원본을 열지 못한 경우) 전처럼 이름으로 찾고 그렇다고
적는다. 과제 밖 입구는 이름(`oos-`)으로 찾는다 — 계약상 이름이 보존된다.

**생성물의 data-action 하나는 원본 무리 하나에만 센다** (11-12d). 값이 같은 무리(0~9 숫자판
셋 — 계좌번호 · 금액 · 비밀번호)가 서로를 찾지 않도록, 장마다 생성물의 data-action 마다 그
요소들의 값이 가장 많이 덮는 원본 무리 하나에 붙인다 (00 까지 있는 숫자판은 num 11개로 pw ·
acc-num 10개를 이긴다). 동점이면 차례로 가른다:

1. 그 생성물 화면의 바탕 원본 화면(계획의 `screens[].from`)에 있던 무리 — 원본 걷기가 잰 그
   무리의 원본 화면과 견준다
2. 이름이 같은 무리
3. 그래도 같으면 그 칸에 "같은 값" 이라고만 적고 줄에 "값이 같은 무리: <이름들>" — ● 도 ○ 도
   아니고 찾은 수에도 넣지 않는다 (세 기준값 실행에는 없다)

| 줄 | 무엇으로 찾나 | 원본 화면 칸 (출처) |
|---|---|---|
| 과제 단계 | 흐름 명세 steps 의 걸음마다 그 장 | 계획의 `from` (계획) |
| 선택지 무리 | 최종 검사의 `choice_groups_original` 중 숫자판이 아닌 것 — 원본의 값 | 원본을 걸어 그 원본 이름이 그려진 화면 (도구 확인) |
| 입력 수단 | 숫자판 (원본의 값이 모두 1~3자리 숫자인 무리 — 원본의 값) · 빌드에서 data-action 이 붙은 `input · textarea · select` (이름) | 원본을 걸어 봄 (도구 확인) |
| 오류 회복 | 흐름 명세 error_paths 마다 오류 장 (회복 조작 · 되돌아가는 장) | 과제의 원본 흐름의 오류 화면 → 되돌아가는 화면 |
| 과제 밖 입구 | 과제 파일의 `entrances` — 그 data-action 이름, 줄 이름은 원본 aria-label | 과제 파일의 화면 (연구자 확정) |

원본 걷기 (`walk.survey`): 그림을 찍기 전에 원본 HTML 을 그 과제의 흐름(과제 파일의 `flow`)
대로 한 페이지에서 한 번 걷고, 걸음마다 그려진 data-action 을 그 요소의 화면(가장 가까운
`[data-screen]`, 없으면 그때 켜진 화면)으로 센다. 스크롤에 가려진 것도 센다. 걸음마다 선택지
무리의 값도 모은다 — 검사 I 가 원본을 걸으며 쓰는 조각(`probes.CHOICE_GROUPS`)을 그대로 쓰고
걸음들을 합친다 (검사 I 의 `original_choices` 와 같은 목록 — 이체 pick-bank 67 · num 11 ·
pw 10 · acc-num 10 · quick 4, 공과금 menu-item 289 · pick-bill 18 · pw 10). 이체 · 공과금
모두 3초 안. 결과는 `storyboard.json` 의 `original`.

세 기준값 실행에서 값으로 찾은 결과:

### 8. 다시 그리기 (`--regions-from`)

이미 모델로 만든 설계서를 새 형식으로 다시 뽑을 때 — 영역 묶기를 다시 부르지 않고 저장된
`storyboard.json` 의 영역 답(영역 · 이름 · 설명 · 출처 꼬리표 · 화면 이름 · 빈 상태 표시)을
그대로 쓴다. 그림 · 누르기는 새로 한다 (그래야 새 형식의 칸이 생긴다).

- **요소 번호가 같을 때만.** 요소가 있는 장의 목록이 같고, 장마다 번호 · 종류(요소 / 무리) ·
  data-action 이 차례대로 같아야 한다 (글자 · 위치는 보지 않는다). 다르면 만들지 않고 (종료 2)
  장마다 처음 다른 곳을 적는다 — "scr-home 의 요소가 다르다 - 저장된 답 30개 · 이번 29개, …".
- 그 파일이 그 실행의 `storyboard/` 안에 있어도 된다 — 폴더를 지우기 전에 읽고, 읽은 것을
  `regions.from.json` 으로 새 폴더에 남긴다 (멈춰도 남는다).
- 맨 앞장의 "영역 묶기" 칸은 "저장된 영역 답을 다시 씀" (그때 모델 · 실행 · 시각 · 그때 비용).
  `regions_call.reused` 에 같은 것이 남고, 이번 비용은 0 이다.

### 9. 그리기

`storyboard.json` 하나로 그린다 (`render.render`). 화면마다의 장 맨 위에 정보칸 한 줄
(화면 ID 와 꼬리표 · 화면 이름과 출처 · 경로 · 원본 화면 · 조건별 화면이면 조건)이 있고, 그림
칸은 그만큼 낮다 (560 × 620px). 긴 그림은 한 장에 들도록 여러 단으로
잘라 나란히 놓는다 (가장 크게 보이는 단 수, 배율은 1 이하). 영역 테두리(굵게, 번호)와 요소
테두리(점선, `e` 번호)는 HTML 로 얹으므로 PDF 를 확대하면 선과 번호가 선명하다. 표가 한
장을 넘으면 인쇄에서 다음 쪽으로 이어진다.

| `features` | 기능-화면 표 — `columns` (본 장 id) · `rows[]` (`section` · `key` · `cells` · `original` · `original_from` · 무리마다의 칸) · `missing`. 선택지 · 숫자판 줄은 `by` (value · name) · `values` (원본 값 수) · `found` (찾은 값 수) · `actions` (빌드의 data-action), 칸은 {`mark` · `found` · `of` · `actions` · `sheets` · `found_conditional`?}. 이름으로 찾은 줄의 칸은 {`mark` · `count` · `sheets`} |
| `changes` · `diagnosis` | 계획의 변경(대응 진단의 문제 글까지) · 진단 (수 · 근거 종류 · 화면별 · 목록) |

| `counts` | 장 · 본 장 · 항목 · 요소 · 누르기 수 |
| `sheets[]` | 장마다 `id` · `screen` · `kind` · `main` · `of` · `condition` · `purpose` · `title` (영역 묶기의 화면 이름) · `name` · `name_source` (model · plan · screen) · `path` (장 id 목록) · `picture` · `size` · `grown` · `clipped` · `covered` · `items[]` (`no` · `kind` · `action` · `text` · `aria` · `box` · `disabled` · `entrance` · `group` · `result`) · `regions[]` (`no` · `name` · `description` · `elements` · `box` · `source` · 빈 상태면 `empty`) · `conditions` |
| `regions_call` | 영역 묶기 호출 — 모델 · mock · 호출마다(첫 · 다시) 그림 수 · 토큰 어림 · 실측 토큰 · 비용 · 걸린 시간 · 문제 · 파일, 전체 비용, `fallback`, `error`. `--regions-from` 이면 `reused` (파일 · 실행 · 시각 · 그때 비용) 와 그때의 모델 · mock |

## 한계

- **눌러 본 것은 그 상태의 한 번이다.** 같은 버튼이 입력값에 따라 다르게 가는 설계(예: 맞는
  계좌면 다음, 틀리면 오류)는 흐름 명세가 적은 상태에서 누른 결과만 적힌다 — 다른 갈래는
  오류 경로 · 펼치기의 조건별 장으로만 보인다.
- **선택지 무리는 대표 하나만 누른다.** 나머지가 같은 곳으로 간다는 것은 확인하지 않았다.
- **1.2초보다 늦게 넘어가는 화면 전환은 "같은 화면에서 바뀜" 으로 적힌다.**
- **덮개 아래에 깔린 요소는 뺀다** (수만 적는다). 모달이 떠 있는 상태의 뒤 화면 버튼이 그렇다.
- **8,000px 넘는 화면은 잘린다.** 잘린 아래쪽 요소는 그 장의 요소에 들어가지 않는다.
- **글자로 된 아이콘(☺ ⌕ 같은 기호)은 X 상자로 바뀌지 않는다** — 글자이기 때문이다.
- **묶음 상자는 원래 스타일로 짐작한다.** 바탕색이 뒤와 다르거나 그림자 · 네 변 테두리가 있던
  요소만 상자가 된다 — 여백만으로 나뉜 묶음은 상자가 되지 않는다.
- **기능-화면 표는 장에 보인 것만 센다.** 선택지 · 숫자판은 값으로 찾으므로 빌드가 다른
  이름으로 그려도 찾지만(mock pass 의 `amt-num` · `amt-set`), 흐름이 머무르지 않는 상태에서만
  보이는 목록(그 실행의 은행 목록 · 비밀번호 숫자판, 저장된 이체 답의 증권사 탭)은 어느 장에도
  없어 세지 못한다. 검사 I 는 문서 전체의 글자로 세므로 그 빌드도 통과한다.
- **값이 같은 무리는 그 화면의 바탕 원본 화면으로 가른다.** 생성물의 이름 하나는 원본 무리
  하나에만 세므로 0~9 숫자판 셋이 서로를 찾지 않지만, 동점은 계획의 `screens[].from` (모델이
  쓴 것)으로 가른다 — 계획이 바탕 화면을 틀리게 적었으면 틀리게 가른다. 그것으로도, 이름으로도
  가르지 못하면 "같은 값" 으로만 남는다.
- **이름 하나가 두 무리의 값을 함께 가지면 많이 덮는 쪽으로만 센다.** 한 단추 무리가 두
  기능의 값을 섞어 그렸으면 적게 덮이는 무리의 값은 그 이름에서 세지 않는다.
- **한글 값은 뒤에 말이 붙은 다른 단추에서도 찾아진다** (검사 I 의 경계 규칙 그대로). 공과금
  menu-item 의 짧은 값이 "2,160원 납부하기" 같은 단추에서 잡혀 빌드의 이름에 `submit-payment`
  가 섞인다.
- **와이어플로의 작은 그림은 화면 위쪽(폰 한 화면)만 보인다.** 전체는 그 장에 있다.
- **`--regions-from` 은 번호가 같아야 쓴다.** 빌드나 도구가 바뀌어 요소 번호가 달라졌으면 모델로
  다시 묶어야 한다.
