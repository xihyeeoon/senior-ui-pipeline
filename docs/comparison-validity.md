# 이 비교로 말할 수 있는 것과 없는 것

**닫힌 문서 (2026-09-30).** 결론: 두 갈래에 같은 조건을 줄 수 없어 직접 비교하지
않기로 했다. DesignRepair 계열은 보관 자료로 남기고 파이프라인에서 뺀다.
아래는 그 판단에 이른 경위와 근거다.

2026-09-30 작성. 규칙 기반과 LLM 재구성을 나란히 놓은 결과를 어디까지 주장할 수
있는지 점검한 기록이다. **결론부터: 지금까지 문서에 적혀 있던 "규칙 기반은 구조를
못 바꾼다"는 이 실험이 보여준 것이 아니다.** 두 갈래가 서로 다른 조건을 받았고,
그 조건 차이가 결과 차이를 설명한다.

## 1. 두 갈래가 받은 조건

| | 규칙 기반 (DesignRepair) | LLM 재구성 |
|---|---|---|
| 입력 단위 | **화면 하나씩** (8번 나눠 호출) | **파일 전체** (8화면 + 전환 스크립트) |
| 전환 스크립트 | **보지 못함** — `split_screens.py` 가 의도적으로 제외 | 전부 봄 |
| 화면 간 이동 | 알 수 없음 | 알 수 있음 |
| 구조 변경 | **검사기가 금지** (`derived_from_original: true` — `data-action`·`id`·`data-screen` 이 사라지면 fatal) | 자유 (`false` — 해당 검사 생략) |
| 규칙 | `senior_kb.csv` 46개 제공 | 주지 않음 |

`tools/split_screens.py` 의 주석이 그 의도를 직접 적고 있다.

> Splitting gives each screen its own page and its own file, and **keeps the
> script out of the model's hands entirely.**

화면 하나만 보는 모델이 "이 화면을 둘로 나눠라" 또는 "이 화면을 없애라"고 판단할
길은 없다. 볼 수 있는 것이 그 화면뿐이기 때문이다. 그리고 설령 나눴다 해도 검사기가
fatal 을 냈을 것이다.

**따라서 "구조를 못 바꿨다"가 아니라 "구조를 바꿀 수 없는 조건을 주었다"가 맞다.**

## 2. fatal 7건은 구조와 무관하다

`outputs/audit.json` 의 fatal 을 분류하면 이렇다.

| 검사 | 내용 | 종류 |
|---|---|---|
| B ×4 | `alert('1원이 전송됩니다.')` 를 주입하고 금액을 `1` 로 하드코딩 | 코드 생성 품질 |
| A ×1 | `data-action="back-recipient"` 를 지움 | 코드 생성 품질 |
| C ×1 | `data-action="back"` 을 만들었으나 처리기에 분기가 없음 | 코드 생성 품질 |
| — | 구조를 바꾸지 못해서 난 fatal | **0건** |

일곱 건 모두 "규칙 기반이 화면을 잘못 고쳤다"는 증거이지 "구조를 못 바꿨다"는 증거가
아니다. 전자는 도구의 코드 생성 품질 문제이고, 후자와는 다른 주장이다.

## 3. KB 에는 구조 규칙이 있다

46개 중 화면·단계·흐름을 언급하는 규칙이 11개다. 그중 둘은
`restructure-changelog.md` 가 "해당 없음" 이라고 적은 변경에 정면으로 대응한다.

| changelog 판정 | 실제로 있는 규칙 |
|---|---|
| #11 account 화면 분할 — "해당 없음" | **SDF-G2-3** 한 화면에 제시하는 정보와 선택지의 수를 제한한다 |
| #12 예금주 확인 화면 신설 — "전용 규칙 없음" | **SDF-G9-3** 되돌릴 수 없는 처리 전에는 확인 단계를 제공한다. 처리 대상과 내용을 다시 보여주고 사용자가 검토할 수 있게 한다 |

그 밖에 SDF-G2-2(주된 흐름과 부가 정보 분리), SDF-G5-1(여러 단계 과업의 진행 표시),
SDF-G10-3(단순한 화면 구성) 도 구조에 닿는다.

그러므로 **"KB 가 구조를 다루지 못한다"** 역시 근거가 약하다. 규칙은 있었고, 도구가
그것을 쓸 수 있는 조건이 아니었거나, 사후 대조에서 엄격하게 판정한 것이다. 그
판정은 재구성본을 만든 쪽이 스스로 매긴 것이라 한쪽으로 기울 수 있다 —
changelog 자신도 그렇게 밝히고 있다.

## 4. 그래서 지금 말할 수 있는 것

**말할 수 있다**

- 이 조건에서 규칙 기반 수리는 화면 안의 속성을 고쳤다. 저대비 텍스트 66 → 56
  (15% 감소), 화면 수·`data-action`·`id` 는 그대로.
- 그 과정에서 회귀가 생겼다. 원본에 없던 `alert()` 주입, 컨트롤 삭제, 죽은 컨트롤.
- LLM 재구성은 구조를 바꾸고 검사를 통과했다. 저대비 66 → 3.
- 재구성을 3회 반복하면 화면 수가 9·7·8 로 갈라지는데 검사기는 셋을 구분하지 못한다.
  (이 주장은 세 재구성본이 **같은 조건**을 받았으므로 유효하다.)

**말할 수 없다**

- 규칙 기반이 구조를 바꿀 능력이 없다. → 그럴 기회를 주지 않았다.
- KB 에 구조 규칙이 없다. → 11개 있다.
- 규칙 기반보다 LLM 재구성이 낫다. → 두 갈래가 같은 조건을 받지 않았다.

## 4-1. 구조 검사를 빼고 다시 검사해 본 결과 (2026-09-30 실측)

기존 데이터만으로 할 수 있는 확인을 했다. 같은 수리본을
`tools/flows/original_fair.json`(원본 흐름과 동일하되 `derived_from_original: false`)
으로 다시 검사했다. 빌드는 손대지 않았고, 원본 흐름 파일도 그대로 두었다.

| | 구조 보존 강제 (`original`) | 구조 검사 면제 (`original_fair`) |
|---|---|---|
| fatal | 7 | **6** |
| warning | 47 | **21** |

- **warning 26건이 사라졌다.** 기존 "warning 47" 의 절반 이상은 원본과 화면을
  맞대어 보는 검사(E: 줄바꿈·높이 증가 등)에서 나온 것이고, 구조를 바꾸는 설계라면
  애초에 받지 않는 검사였다.
- **남은 fatal 6건은 전부 코드 생성 품질이다.** `alert()` 주입 5건, 죽은 컨트롤 1건.
- 사라진 fatal 1건은 `data-action="back-recipient"` 삭제 — 구조 보존 검사 항목이었다.

따라서 공정한 조건에서도 규칙 기반 수리는 검사를 통과하지 못하지만, **그 이유는
구조를 바꾸지 못해서가 아니라 화면을 잘못 고쳤기 때문이다.** 이 둘은 다른 주장이다.

두 검사 결과는 뷰어의 빌드 표에 나란히 표시된다.

## 4-2. 조건을 맞춰 다시 돌려 본 결과 (2026-09-30 실행)

파일 전체를 한 번에 주고 `tools/run_whole.py` 로 1회 실행했다. 모델(gpt-4o)과
KB(senior_kb.csv 46개)는 그대로 두고 **입력 단위만** 바꿨다. 과제 설명은 주지
않았다 — "태스크 맥락이 있어야 구조가 바뀐다" 는 별개 가설이라 변수를 섞지 않기
위해서다.

### 결과: 실행이 중간에 실패했다

```
openai.RateLimitError: 429 - Request too large for gpt-4o ...
  tokens per min (TPM): Limit 30000, Requested 39276
```

**요청 자체가 계정 한도보다 크다.** 재시도로 풀리는 오류가 아니다. 433초 만에
B 스트림(property, senior_kb.csv 를 쓰는 쪽)에서 죽었고, 최종 병합본은 나오지
않았다.

Playwright 가 뽑은 요소 수가 원인을 보여준다.

| | 전체 파일 | 화면 하나 (account) |
|---|---|---|
| Clickable | 51 | 13 |
| Spacing | 56 | 8 |
| Label | 50 | 12 |
| Text | **295** | 8 |

`tools/run_screens.py` 의 주석이 이미 이 사실을 적고 있었다 — "this account's
gpt-4o TPM budget is 30k and a single property prompt is 10-15k tokens".
화면 하나가 10~15k 이면 여덟 화면은 한도를 넘는다.

### 그래서 답하지 못한 것

senior_kb.csv 를 쓰는 B 스트림이 돌지 않았으므로 **"전체 파일을 보면 규칙 기반이
구조를 바꾸는가" 는 여전히 미답이다.** SDF-G2-3·SDF-G9-3 이 발화하는지도 확인하지
못했다.

### 답한 것 (A 스트림만)

component 스트림(Material Design KB)은 끝까지 돌았다. 바뀐 것은 5곳, 전부 버튼
레이블이다.

| 원본 | A 스트림 결과 |
|---|---|
| 다음 | 다음 단계 |
| 보내기 | 보내기 시작 |
| 확인 | 확인 완료 |
| 쿠폰바로받기 | 쿠폰 바로 받기 |

구조 지표는 하나도 움직이지 않았다 — 화면 8→8, `data-action` 23→23, `id` 16→16,
줄 수 597→597. 검사 결과는 `outputs/audit_whole_comp.json` 에 있다: fatal 0,
warning 12, **저대비 66→66**. 고령자 관점의 개선은 0인데, 그 일을 하는 것이
senior_kb.csv 이고 그 단계가 실행되지 않았으니 당연한 결과다.

근거가 "sentence case for button label text" 라는 Material Design 규칙인 것도
짚어 둘 만하다. 한국어에는 대소문자가 없다.

### 이 실행이 새로 알려 준 것

두 갈래의 조건 차이가 **방법론적 선택이 아니라 인프라 제약**이었다.
`split_screens.py` 가 화면을 쪼갠 것은 "DesignRepair 가 한 페이지씩 분석하므로"
라고 적혀 있지만, 실제로는 전체 파일을 넣으면 API 한도에 걸려 **돌지 않는다**.
지금 계정에서 두 갈래에 같은 입력 단위를 주는 것은 불가능하다.

따라서 `comparison-validity.md` 5절 1번(같은 입력 단위)은 계정 한도를 올리거나
다른 방법을 찾기 전에는 실행할 수 없다.

## 5. 여기서 닫는다

공정한 비교에는 두 갈래에 같은 입력 단위를 주는 것이 필요했다. 4-2절에서 시도했고,
API 한도 때문에 **불가능하다는 것이 확인됐다.** 지금 계정에서 DesignRepair 에
파일 전체를 넣으면 property 프롬프트가 39,276 토큰이 되어 30,000 TPM 한도를 넘는다.
한도를 올리거나, 중간 단위로 묶거나, 모델을 바꾸는 방법이 있지만 어느 쪽도
"변수 하나만 바꾼다" 는 조건을 지키지 못한다.

**따라서 두 결과를 직접 비교하지 않는다.** 규칙 기반이 구조를 바꿀 수 있는지는
이 연구가 답하지 않는 질문으로 남긴다. 결론을 내지 않는 것이 지금 자료로 할 수
있는 가장 정확한 처리다.

DesignRepair 결과와 `kb/senior_kb.csv` 는 지우지 않고 보관 자료로 남긴다.
`vendor/designrepair/` 도 그대로 둔다. 파이프라인에는 쓰지 않는다.

덧붙여, 도구의 목적이 애초에 다르다는 점도 이 결정에 들어 있다. 이 연구의 도구는
디자이너에게 **구조 시안**을 주는 것이 목표이고 시각 디테일은 디자이너가 채운다.
DesignRepair 는 완성된 화면의 시각 품질을 다듬는 도구다. 같은 자를 대는 것이
처음부터 맞지 않았다.

## 6. 이 문서가 생긴 경위

대시보드에 규칙 기반이 파이프라인 단계처럼 보인다는 지적에서 시작해, "규칙 기반이
실패한 것이 방법의 한계가 아니라 구현이 잘못돼서일 수 있지 않나" 라는 질문으로
이어졌다. 확인해 보니 그 지적이 맞았다. fatal 7건을 실제로 읽어 보지 않고
"구조를 못 바꾼다" 는 해석을 붙인 것이 문제의 출발점이었다.
