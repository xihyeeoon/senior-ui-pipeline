# 디자이너용 변경 설명서

최종: 생성 (시도 3)

실행 `20261008-125219-bill` · 시도 3 에서 검사를 통과한 빌드 · 커밋 `3468b75658b7`.

이 파일은 구조 시안의 설명이다. 색·글꼴·간격 같은 시각 디테일은 평가하지 않았다. 화면 구성과 흐름, 그리고 바꾼 이유를 옮겨 적는다.

## 화면 대응

| 원본 | 재설계 |
|---|---|
| home | home |
| menu | menu, search |
| search | search |
| bill-home | bill-start |
| camera | capture |
| info | review |
| password | authenticate |
| done | receipt |

재설계 화면의 순서와 하는 일:

1. `home` — 글자로 표시된 전체메뉴 또는 메뉴 검색을 선택해 납부 메뉴 찾기를 시작한다.
2. `menu` — 세금·공과금 납부 진입을 찾거나 원본의 모든 분야와 메뉴를 선택한다.
3. `search` — 검색어를 입력하거나 전체 메뉴 목록에서 납부 진입을 선택한다.
4. `bill-start` — 종이 고지서 촬영을 시작하거나 조회·등록·공과금 종류 기능을 선택한다.
5. `capture` — 고지서를 맞춰 촬영하고 사진과 인식 상태를 확인한다.
6. `review` — 고지서와 납부정보를 비교하고 출금계좌를 확인한 뒤 비밀번호 단계로 간다.
7. `authenticate` — 출금계좌 비밀번호 네 자리를 입력·수정하고 명시적으로 납부를 요청한다.
8. `receipt` — 처리 결과와 납부 내역을 확인하고 홈으로 돌아간다.

- **D11** `info` 납부정보 표 — 긴 번호와 행 이름을 눈으로 연결하기 어렵고 청구연월을 날짜로 해석해야 한다. 고지서와 비교해야 할 고객명·청구월·금액이 여러 번호 사이에 흩어져 있다. (근거[화면]: 그림 13에는 전자납부번호가 첫 행에 있고 청구연월은 202607로 표시된다. 고객전용지정 계좌번호라는 이름은 두 줄로 갈라지고 긴 값은 오른쪽에 붙는다. 납부금액은 정보 표의 마지막 행에 있다.)

- **D13** `info` 하단 납부 버튼과 뒤로가기 — 납부 버튼을 누르면 즉시 돈이 나가는지 다음 확인 단계로 가는지 알 수 없다. 정보가 틀려 뒤로 가면 촬영 화면이 아니라 납부 시작 화면으로 돌아가 재촬영 경로를 다시 찾아야 한다. (근거[화면+코드]: 그림 13의 하단 버튼에는 납부라고만 쓰여 있다. 코드에서 pay는 password로 이동하고, 상단 뒤로가기는 to-bill-home으로 연결되어 있다.)
- **D14** `password` 비밀번호 제목, 숫자판, 수정 조작 — 어느 계좌의 비밀번호인지 화면에서 다시 확인할 수 없다. 숫자판은 익숙한 순서가 아니고 칸 경계가 없어 숫자를 매번 찾아야 하며, 지우기 기호의 뜻을 모르면 잘못 입력한 숫자를 고치기 어렵다. (근거[화면]: 그림 14에는 계좌 비밀번호라는 제목과 원 네 개만 있고 계좌번호·납부금액은 없다. 숫자는 불규칙하게 배치되어 있고 파란 바탕 안에 버튼 경계가 없다. 맨 아래는 재배열과 글자 없는 지우기 기호다.)
- **D15** `password` 네 번째 숫자 입력 이후 — 네 번째 숫자를 잘못 눌러도 고칠 기회 없이 완료로 넘어간다. 잘못된 비밀번호에 대한 안내가 없어 사용자가 인증이 실제로 됐다고 오해할 수 있다. (근거[코드]: pw 처리에서는 입력 길이가 네 자리가 되면 180ms 뒤 done을 보여준다. 비밀번호 검증이나 오류 상태, 별도 납부 확인 버튼은 없다. pay를 다시 누를 때는 S.pw를 빈 값으로 초기화한다.)
- **D16** `done` 완료 제목, 재입금 안내, 확인 버튼 — 납부완료라는 큰 제목과 완료가 표시되어도 재입금될 수 있다는 안내가 충돌해 과업을 끝냈는지 확신하기 어렵다. 확인을 누른 뒤 어디로 가는지도 알 수 없다. (근거[화면+코드]: 그림 15에는 큰 체크 표시와 납부완료 제목 아래에 입금할 수 없는 계좌이면 재입금된다는 작은 안내가 있다. 하단 버튼은 확인이다. 코드에서 finish는 home으로 이동한다.)
- **D17** `done` 납부 상세 내역 — 납부 종류와 청구월을 한눈에 확인하기 어렵고 긴 계좌번호가 행 너비를 대부분 차지한다. 완료 화면을 종이 고지서와 대조하려면 여러 행을 다시 읽어야 한다. (근거[화면]: 그림 15의 제목은 납부완료뿐이며 전기요금이라는 종류는 없다. 청구연월은 202607이고 고객전용지정 계좌번호 행에는 긴 이름과 긴 숫자가 한 줄에 함께 놓여 있다.)

## 과제 밖 입구

과제 경로 위 화면의 다른 메뉴 · 버튼(과제 파일의 `entrances`, 검사 K)이 처음 보이는 자리를 원본과 나란히 적는다. 남아 있는 것과 찾을 수 있는 것은 다르다 (Findlater, McGrenere 2007). 기록만 한다 — 판정 · 고르기에 쓰지 않고, 기준선 · 합격선은 정하지 않았다.

### 검사의 경고 (0건)

### 선택지: 문서에 있는 것과 누를 수 있게 보인 것

검사 I 는 원본의 선택지 값마다 걷는 동안(펼치기 포함) 어느 상태에서 누를 수 있게 보였는지 센다. 원본을 걷는 동안 보이던 값이 생성물에서 어느 상태에서도 보이지 않으면 검사 I 의 fatal 이다 (11-8). 아래는 남은 차이 — 원본도 걷는 동안 보이지 않던 값이고, 실제 앱에서 그 값에 닿는 길이 있는지 사람이 본다.

없음

### 선택지가 아니라고 선언한 무리

원본에서 같은 `data-action` 을 가진 형제 무리지만 과제 파일(`not_choices`)이 선택지가 아니라고 선언한 것이다. 검사 I 는 이 무리가 남았는지 세지 않았다.

| `menu-tab` | 7 | 분야로 스크롤하는 탭 — 찾아가는 수단 |

## 선택지 데이터의 출처

선택지 목록(MENU_BANK 79, MENU_CARD 77, MENU_STOCK 72, MENU_INSURE 55, MENU_BENEFIT 41, MENU_GOODS 18, MENU_HELP 12, BILL_ITEMS 23, PW_KEYS 10, MENU_TABS 7)은 `window.PRESERVED` 에서 온다 — 도구가 원본 HTML 에서 꺼내 재설계 HTML 의 `<script id="preserved-data">` 에 넣은 것이다. 목록을 실제 앱으로 옮길 때는 이 블록을 출처로 쓴다.
