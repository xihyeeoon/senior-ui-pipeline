## 1. 과제

아래는 은행 앱의 세금·공과금 납부 화면을 HTML 한 파일로 만든 것이다 (8화면). 65세 이상 고령 사용자가
**공과금 납부 과업 — 전체메뉴나 메뉴 검색에서 납부하기 찾기, 종이 고지서 촬영, 납부정보 확인, 계좌 비밀번호, 완료 —
을 혼자서 끝낼 수 있도록** 이 화면들을 다시 설계하라.

아래 "계획" 은 이 원본을 진단해 세운 것이다. 이 계획대로 설계하라.

- 화면은 계획의 `screens` 와 같아야 한다. 각 화면의 `data-screen` 은 `screens[].name` 과
  한 글자도 다르지 않아야 하고, 계획에 없는 화면을 더하지 마라. 어긋나면 형식 오류로
  돌아온다.
- 계획에 없는 큰 변경(화면 추가·삭제·순서 변경, 과업 경로 변경)은 하지 마라. 글자·크기·
  배치 같은 세부는 네가 정한다.
- 원본의 다른 메뉴와 버튼도 사용자가 쓸 수 있는 기능이다. 배치 · 묶음 · 크기는 바꿔도 되지만 없애지 마라.
- 서버도 카메라도 없다. 고지서 촬영처럼 기기·서버가 하던 일은 원본에 있는 동작만, 원본이 보여 주는 값으로 흉내 낸다. 흉내 낸다는 것을 화면에 쓰지는 않는다.
- 화면의 모든 글은 한국어로 쓴다. 영어 단어를 새로 넣지 않는다.

## 2. 지켜야 할 기술 계약 (검사기가 이 형식으로 화면을 몰고 다닌다)

- 파일 하나. 외부 자원 없음. `<html lang="ko">`.
- `<div id="phone">` 안에 화면들. 폭 390px, 높이 844px.
- 화면 하나는 `<section class="screen" data-screen="이름">`. 보이는 화면에만 `on` 클래스.
  화면 이름은 영문 소문자.
- 모든 조작은 `data-action="이름"` 속성으로 표시하고, `#phone` 에 붙인 **하나의** 클릭
  처리기 안에서 `const a = el.dataset.action;` 뒤 `if(a==='이름'){…} else if(a==='이름'){…}`
  형식으로 분기한다. 처리되지 않는 `data-action` 을 남기지 마라. `onclick` 속성, `alert()`,
  `confirm()`, `prompt()` 는 쓰지 마라.
- 원본의 과제 밖 입구(data-action 이 oos- 로 시작하는 요소)는 data-action 이름을 원본 그대로
  둔다. 글자 · 배치 · 묶음은 바꿔도 된다.
- 숫자판은 버튼마다 `data-action` 과 `data-v="숫자"` 를 둔다.
- 전역에 `window.__screen()` (현재 화면 이름 반환)을 둔다.
- 완료 화면에는 납부한 금액을 담는 `id="dn-paid"` 요소와 전자납부번호를 담는 `id="dn-eno"`
  요소가 있어야 한다. 금액 텍스트는 `2,160` 처럼 천 단위 쉼표 숫자여야 한다.
- 과업: **종이 고지서로 공과금을 낸다.** 사용자는 납부 메뉴를 찾아 들어가 고지서를 촬영하고,
  읽힌 납부정보(전자납부번호 · 고객명 · 금액 · 출금계좌)를 확인한 뒤 계좌 비밀번호를 넣는다.
  납부정보는 고지서에서 읽히는 값이므로 원본이 보여 주는 값을 그대로 보여 준다.
- **검색어를 미리 채워 넣지 마라.** 메뉴 검색을 둔다면 검색창은 빈 채로 시작한다.
- **확인 화면을 생략하지 마라.** 납부정보를 보여 주고 사용자가 확인한 뒤 납부하는 화면이 있어야 한다.
- **원본에 있던 선택지는 하나도 빠뜨리지 마라.** 스크립트 배열로 그려지는 목록은 도구가
  `window.PRESERVED.<이름>` 으로 넣어 준다 (아래 "원본이 가진 선택지" 참고). 그 목록을
  직접 타이핑하지 말고 그 이름을 참조해 그려라 - 참조하라고 한 이름을 하나라도 읽지 않으면
  형식 오류로 돌아온다. 선택지를 몇 개, 어떤 순서, 어떤 묶음으로 보일지는 네가 정한다.
  다만 모든 값을 고를 수 있어야 하고, **선택 화면이 열렸을 때 모든 값이 DOM 안에
  있어야 한다** (숨김·접힘은 괜찮다). 다만 접거나 숨긴 값도 흐름 명세의 걸음이나
  `reveal` 을 따라가면 어느 상태에서든 실제로 누를 수 있게 보여야 한다 — 접은 묶음마다(값이
  하나뿐인 묶음도) 펼치는 조작을 `reveal` 에 적어라. 검색창을 두더라도 검색어가 비었을 때는 전체
  목록이 DOM 에 있어야 한다. 눌러야 목록이 만들어지는 설계라면 그 조작을 흐름 명세의
  `reveal` 에 적는다.
- 화면의 글은 실제 앱처럼 쓴다. 서버가 없다는 것, 흉내 낸 처리라는 것, 연습이라는 것을
  화면 문구로 알리지 마라 ('연습용', '모의', '시제품' 같은 말을 화면에 넣지 않는다).
- 마크업에서 쓰는 클래스는 모두 `<style>` 안에 정의하라.

## 원본이 가진 선택지

원본의 반복 선택지 (스크립트가 런타임에 그린다):
  menu-item — 289개 (MENU_BANK 79 + MENU_CARD 77 + MENU_STOCK 72 + MENU_INSURE 55 + MENU_BENEFIT 41 + MENU_GOODS 18 + MENU_HELP 12)
  pick-bill — 18개 (BILL_ITEMS 23)
  pw — 10개 (PW_KEYS 10)

이 데이터는 도구가 다음 이름으로 넣어 준다:
  window.PRESERVED.MENU_BANK (79개) · window.PRESERVED.MENU_CARD (77개) · window.PRESERVED.MENU_STOCK (72개) · window.PRESERVED.MENU_INSURE (55개) · window.PRESERVED.MENU_BENEFIT (41개) · window.PRESERVED.MENU_GOODS (18개) · window.PRESERVED.MENU_HELP (12개) · window.PRESERVED.BILL_ITEMS (23개) · window.PRESERVED.PW_KEYS (10개)

목록을 직접 쓰지 마라. 이것을 참조해 그려라. 선택지를 몇 개, 어떤 순서, 어떤
묶음으로 보일지는 네가 정한다. 다만 모든 값을 고를 수 있어야 한다.
위 이름을 하나도 빠뜨리지 말고 참조하라 - 읽지 않은 이름이
있으면 형식 오류로 돌아온다. 읽는 모양은 `window.PRESERVED.MENU_BANK` · `const P = window.PRESERVED; P.MENU_BANK` · `const {MENU_BANK} = window.PRESERVED` 모두 된다.

검사가 보는 것은 렌더링된 화면이다. 선택 화면이 열렸을 때 모든 값이 DOM
안에 있어야 한다 (숨김·접힘은 괜찮다). 검색창을 두더라도 검색어가 비었을
때는 전체 목록이 DOM 에 있어야 한다. 눌러야 목록이 만들어지는 설계라면
그 조작을 흐름 명세의 `reveal` 에 적어라.
도구가 넣어 준 데이터 블록은 증거로 세지 않는다 - 그 데이터를 읽어 **그린** 것만 센다.

선택지가 아니라고 과제가 정한 반복 요소 (검사가 선택지로 세지 않는다):
  menu-chip — 60개: 분류로 스크롤하는 표지판 — 찾아가는 수단
  menu-tab — 7개 (MENU_TABS 7): 분야로 스크롤하는 탭 — 찾아가는 수단
그 값도 도구가 넣어 준다: window.PRESERVED.MENU_TABS (7개).
써도 되고 쓰지 않아도 된다 - 읽지 않아도 형식 오류가 아니다.

## 3. 흐름 명세도 함께 출력하라

검사기는 화면을 어떻게 지나가는지 모른다. 네가 만든 설계를 검사기가 처음부터 끝까지 몰고
갈 수 있도록 **흐름 명세 JSON** 을 HTML 과 함께 출력하라. 형식은 다음과 같다.

```json
{
  "name": "auto",
  "note": "한 줄 설명",
  "derived_from_original": false,
  "required_ids": ["phone", "dn-paid", "dn-eno", "..."],
  "steps": [
    {"screen": "<시작 화면 이름>"},
    {"screen": "<다음 화면 이름>", "click": "<누를 요소의 선택자>"},
    {"screen": "<다음 화면 이름>", "do": [
      {"click": "<선택자>"}
    ]},
    {"screen": "<완료 화면 이름>", "do": [
      {"repeat": 4, "click": "#pwpad [data-action='pw']", "wait": 0.15}
    ]}
  ],
  "expect": {}
}
```

규칙:
- `steps` 는 검사기가 지나가는 순서. 각 항목의 `screen` 은 그 단계를 수행한 **뒤에 도착해
  있어야 할** 화면 이름(`data-screen` 값)이다. 첫 항목은 시작 화면이고 동작이 없다.
- 한 단계의 동작은 `click` 하나이거나 `do` 배열이다. `do` 의 항목은 `{"click": 선택자}`,
  `{"type": 문자열, "key": 선택자틀}` (문자열의 글자마다 `%s` 자리에 넣어 클릭),
  `{"repeat": n, "click": 선택자, "wait": 초}`, `{"wait": 초}` 중 하나.
- 치환 문자열: `{AMOUNT}` = 2160, `{AMOUNT_SHOWN}` = 2,160, `{ENO}` = 1700000000,
  `{CUSTOMER}` = 홍길동, `{PAY_BANK}` = 신한, `{PAY_ACCOUNT}` = 110-000-000000, `{QUERY}` = 공과.
  `{QUERY}` 는 **검사기가 메뉴 검색창에 눌러 넣을 값**이고, 나머지는 고지서에서 읽혀 화면에
  보여야 할 값이다. 설계에 검색어를 미리 채워 두라는 뜻이 아니다.
- `steps` 는 홈에서 납부 메뉴를 찾아 납부를 마치는 가장 긴 경로다. HTML 의 모든 화면을 `steps` 가 지나가야 한다.
- `required_ids` 는 네 HTML 에 실제로 있는 id 만 적는다. `phone` · `dn-paid` · `dn-eno` 는 반드시 포함.
- 완료 화면은 `steps` 의 마지막 화면이다 (예시의 `paid` 도 그 설계의 마지막 화면 이름일 뿐이다).
  완료 화면의 `#dn-paid` · `#dn-eno` 가 낸 금액과 전자납부번호를 보이는지는 검사기가 과제에서 읽어 직접
  확인하므로 `expect` 에 적지 않아도 된다. `expect` 는 다른 값을 더 확인하고 싶을 때만 쓰고, 키는 `steps` 의 화면 이름이다.
- 눌러야 목록이 만들어지는 설계라면, 그 조작을 `reveal` 에
  적는다: `"reveal": {"<선택지의 data-action>": {"at": "<steps 의 화면 이름>", "do": [{"click": "<선택자>"}]}}`.
  `do` 의 항목은 `{"click": 선택자}` 하나뿐이다. 누를 것은 `at` 화면에 보이는 `data-action`
  버튼이고, 누른 뒤에도 같은 화면이어야 한다. 검사기는 `at` 까지 간 뒤 `do` 를 하나씩 누르며
  선택지를 모은다. 펼친 뒤에는 모든 값이 `data-action` 요소로 있어야 한다.
- `derived_from_original` 은 `false`.
- 선택자는 네 HTML 에 있는 것만 쓴다. 검사기는 없는 선택자에서 멈춘다.
